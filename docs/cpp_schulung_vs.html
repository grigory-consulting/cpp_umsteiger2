Warum ist C++ relevant?

  • Performance: direkt an der Hardware, ohne JIT/GC-Overhead. C++ ist der Maßstab, an dem sich andere Sprachen messen.
  • Multi-Paradigma: prozedural, objektorientiert, generisch, funktional in einer Sprache.
  • Zero-Cost-Abstraktionen: was du nicht benutzt, kostet nichts; was du benutzt, könntest du nicht effizienter selbst schreiben.
  • Überall einsetzbar: von 8-Bit-Mikrocontrollern bis zum Supercomputer. Eine Sprache, alle Skalen.
  • Reife: 40 Jahre Erfahrung, Standard-Library, Tooling (Sanitizer, Profiler, Static Analysis).
  • Aktive Evolution: alle drei Jahre neuer Standard. C++26 mit Reflection und Pattern Matching steht vor der Tür.

Modernes vs. klassisches C++

„Modernes C++“ (ab C++11) sieht anders aus als das C++ aus den 1990ern.

Klassisches C++ (vor C++11)

char* name = new char[64];
strcpy(name, "Sensor-1");
// ... viel Code ...
delete[] name;       // leicht zu vergessen
  • Manuelle Speicher-Verwaltung
  • Roh-Pointer überall
  • C-Strings (char*)
  • Schleifen mit Index-Variable

Modernes C++ (ab C++11/17/20)

std::string name{"Sensor-1"};
// keine Freigabe nötig: RAII
  • RAII: Ressourcen über Destruktoren
  • Smart Pointer als Default
  • std::string, Range-based for

Variablen & Typen: Kurzreferenz

nullptr statt NULL / 0

Klassisches NULL ist ein Makro für 0, also ein int. Bei Funktions-Überladung führt das zu Mehrdeutigkeiten und stillem Falsch-Aufruf.

void f(int);
void f(char*);

f(NULL);     // ?  ruft f(int) auf, wahrscheinlich nicht gewollt
f(0);        // ?  dito
f(nullptr);  // ✓ ruft f(char*) auf, typsicher
  • nullptr (C++11) hat einen eigenen Typ: std::nullptr_t
  • Implizit konvertierbar zu jedem Pointer-Typ, aber nicht zu int
  • Faustregel: in modernem C++ niemals NULL oder 0 für Zeiger schreiben
  • Auch konvertierbar zu bool → if (ptr) funktioniert weiterhin

enum class: typsichere Aufzählungen

Klassisches enum ist eigentlich nur int mit Namen: globaler Scope, implizite Casts, Namenskollisionen. enum class (C++11) löst alles auf einmal.

enum       Color { Red, Green, Blue };          // alt: Red, Green, Blue global
enum class Mode  { On, Off, Standby };          // neu: Mode::On, gescopet
int n = Red;                                    // alt: implizit OK ⚠
int m = Mode::On;                               // neu: FEHLER, kein impliziter Cast
int k = static_cast<int>(Mode::On);             // neu: Cast nur explizit
enum class Status : std::uint8_t { Ok, Warn };  // eigener Underlying-Typ
  • Gescopet + typsicher: keine Namenskollisionen, keine impliziten Casts nach/von int
  • Vorwärtsdeklarierbar wenn Underlying-Typ angegeben ist (Header-Kompilier-Vorteile)
  • Faustregel: in neuem Code immer enum class

auto & decltype: Typ-Deduktion

Lass den Compiler den Typ bestimmen, wenn er aus dem Kontext eindeutig ablesbar ist. Spart Tipparbeit, vermeidet implizite Konvertierungen.

// auto: Typ wird aus dem Initializer abgeleitet
auto i = 42;                     // int
auto d = 3.14;                   // double
auto s = std::string{"hi"};      // std::string  (NICHT: const char*)
auto& ref   = container[0];      // Referenz
const auto& cref = container[0]; // const-Referenz, keine Kopie
// decltype: übernimmt den Typ eines Ausdrucks (auch ohne Auswertung)
int x = 0;
decltype(x)  y = 5;              // int
decltype(x + 1.0) z = 1;         // double  (Ausdruck wird nicht ausgeführt)
// Trailing return type: Rückgabetyp hängt vom Parameter ab
template <typename T, typename U>
auto add(T a, U b) -> decltype(a + b) { return a + b; }
  • Wann auto? Iteratortypen, Lambda-Returns, lange Template-Typen
  • Wann explizit? Public-API / Signaturen, wenn der Typ als Doku dient
  • auto deduziert ohne & / const → bei Range-for fast immer const auto&

Uniform Initialization mit {}

Eine Syntax für alle Initialisierungen: fundamentale Typen, Klassen, Container, Aggregates. Verbietet zusätzlich stille Genauigkeitsverluste.

int              x{7};                            // Skalar
std::vector<int> v{1, 2, 3, 4};                   // Container, Initializer-List
std::map<std::string,int> m{ {"a",1}, {"b",2} };  // verschachtelt
struct Point { double x, y; };
Point p{1.0, 2.0};                                // Aggregate
Sensor s{"temp-1", 30.0};                         // Konstruktor

// Narrowing, nur Brace-Init schlägt Alarm
int n{3.14};                                      // FEHLER: double -> int
int o = 3.14;                                     // stillschweigend (= 3)

// Vector-Falle: () vs {}
std::vector<int> a(10, 5);                        // 10 Elemente, alle 5
std::vector<int> b{10, 5};                        // 2 Elemente: 10 und 5
  • Faustregel: in neuem Code überall {}, außer wenn ein Konstruktor mit Größen-Argumenten gemeint ist (vector(size, value))
  • Verhindert die Most Vexing Parse (Widget w(); ist eine Funktions-Deklaration!)

Kontrollstrukturen: Kurzreferenz

// if mit Init-Statement (C++17)
if (auto it = map.find(k); it != map.end()) {
    std::cout << it->second << '\n';
}

// switch
switch (mode) {
    case Mode::A: /* ... */ break;
    case Mode::B: [[fallthrough]];
    case Mode::C: /* ... */ break;
    default:      /* ... */;
}

// Schleifen
for (int i = 0; i < n; ++i)            { /* klassisch */ }
for (const auto& v : container)        { /* range-based */ }
while (!done) { /* ... */ }

Range-based for: Lesender Zugriff auf jedes Element, ohne unnötige Kopien (const auto& bindet als const-Referenz).

[[fallthrough]]: Beispiel

enum class LogLevel { Error, Warning, Info, Debug };

void log(LogLevel level, const std::string& msg) {
    switch (level) {
        case LogLevel::Debug:
            std::cout << "[debug] ";
            [[fallthrough]];                                  // -> Info
        case LogLevel::Info:    std::cout << "[info] "    << msg << '\n'; break;
        case LogLevel::Warning: std::cout << "[warning] " << msg << '\n'; break;
        case LogLevel::Error:   std::cout << "[error] "   << msg << '\n'; break;
    }
}

log(LogLevel::Debug, "x") → [debug] [info] x. Ohne [[fallthrough]] würde der Compiler warnen.

Klassen: Initialisierung

Besser: Member direkt initialisieren, statt erst default-erzeugen und dann im Konstruktor-Body zuweisen.

Gut: Member-Initializer-List

class Sensor {
public:
    Sensor(std::string name, double threshold)
        : name_{std::move(name)},
          threshold_{threshold} {}
private:
    std::string name_;
    double      threshold_;
};

Member werden direkt mit den richtigen Werten erzeugt.

Schlecht: Zuweisung im Body

class Sensor {
public:
    Sensor(std::string name, double threshold) {
        name_      = std::move(name);
        threshold_ = threshold;
    }
private:
    std::string name_;
    double      threshold_;
};

Erst default-konstruiert, dann nochmal zugewiesen, bei string, vector, … unnötig teuer; bei const/Referenz-Membern unmöglich.

Klassen: Kapselung & const-correctness

class Sensor {
public:
    Sensor(std::string name, double threshold)
        : name_{std::move(name)}, threshold_{threshold} {}

    const std::string& name() const noexcept { return name_; }

    bool triggers(double value) const { return value > threshold_; }

private:
    std::string name_;
    double      threshold_;
};
  • const std::string& als Rückgabe: Zugriff ohne Kopie, Aufrufer darf nicht ändern
  • name() const: Methode verändert das Objekt nicht (nur lesender Zugriff)
  • noexcept: verspricht: keine Exception
  • bool triggers(double v) const: s.triggers(35.0) → true, falls v > threshold_
  • Trailing underscore (name_) als Konvention für Member

Container, Algorithmen, Iteratoren und eine Übung.

Container-Übersicht

Kategorie Container Typischer Einsatz

Assoziativ map, set (+ multi…) sortierter Schlüssel-Zugriff, Log(n)

Algorithmen & Iteratoren

#include <algorithm>
#include <numeric>
#include <vector>

std::vector<int> v{5, 2, 8, 1, 9, 3};

std::sort(v.begin(), v.end());                            // sortieren
auto it  = std::find(v.begin(), v.end(), 8);              // suchen
int  sum = std::accumulate(v.begin(), v.end(), 0);        // Summe
auto cnt = std::count_if(v.begin(), v.end(),
                         [](int x){ return x > 3; });

std::transform(v.begin(), v.end(), v.begin(),             // in-place
               [](int x){ return x * x; });

Algorithmen + Iteratoren: STL-Algorithmen arbeiten nicht direkt auf Containern, sondern auf Iterator-Bereichen [begin, end). begin() zeigt aufs erste Element, end() auf die Position hinter dem letzten.

std::sort(v.begin(), v.end()); heißt also: sortiere alle Elemente von v.

Iterator-Kategorien

Kategorie Kann Typische Container
input einmal vorwärts lesen Streams
output einmal vorwärts schreiben Streams, back_inserter
forward mehrfach vorwärts laufen std::forward_list
bidirectional vorwärts und rückwärts std::list, std::map
random-access direkter Zugriff wie bei Arrays std::vector, std::array

Iteratoren verbinden Container und Algorithmen. Nicht jeder Algorithmus funktioniert mit jedem Container: z. B. braucht std::sort Random-Access, läuft auf std::vector, aber nicht direkt auf std::list (dort: list::sort() als Member).

Teil III: Funktionen & Parameterübergabe

Parameterübergabe: Faustregel

Mechanismus Syntax Bedeutung Wann verwenden?
By value void f(T x) Funktion bekommt eine Kopie Kleine Typen oder eigene Kopie nötig
By const-ref void f(const T& x) Keine Kopie, nur lesen Große Objekte, die nicht verändert werden
By ref void f(T& x) Keine Kopie, darf verändert werden Wenn die Funktion das Original ändern soll
By pointer void f(T* x) Adresse, kann nullptr sein Optionaler Parameter oder C-APIs
By rvalue-ref void f(T&& x) Darf aus dem Argument „moven“ Move-Semantik / effiziente Ressourcenübernahme

Faustregel: Kleine Werte per Kopie, große nur-lesende Objekte per const&, veränderbare per &, optionale per Pointer, Ressourcen per Move.

Parameterübergabe: Mini-Beispiele

void print(int x);                       // by value: int ist klein
void printName(const std::string& s);    // const-ref: keine Kopie, nur lesen
void normalize(std::vector<double>& v);  // ref: verändert das Original
void setSensor(Sensor* s);               // pointer: darf nullptr sein
void store(std::string&& name);          // rvalue-ref: darf moven

T&& bedeutet nicht automatisch „Ownership“, sondern: Die Funktion darf den Inhalt übernehmen bzw. daraus std::move verwenden.

Für Konstruktoren ist oft die einfachere Variante praktischer, by value + move:

public:
    Sensor(std::string name) : name_{std::move(name)} {}
private:
    std::string name_;

Funktionen: moderne Features

// Standardargument: port ist optional
void connect(std::string_view host, int port = 8080);

// Überladung: gleicher Name, unterschiedliche Parametertypen
int    max(int a, int b);
double max(double a, double b);

// Lambda: anonyme Funktion
auto is_even = [](int x) { return x % 2 == 0; };

// Generic Lambda (C++14): Parametertypen werden automatisch erkannt

  • Default Arguments: Parameter optional machen
  • Überladung: mehrere Funktionen mit gleichem Namen, unterscheidbar an den Parametertypen
  • Lambdas: kleine Funktionen direkt an der Verwendungsstelle definieren
  • constexpr: kann zur Compile-Zeit ausgewertet werden, wenn die Argumente konstant sind (nicht: muss immer)

Return Value Optimization: Return by Value ist meist richtig

std::vector<int> make_data() {
    std::vector<int> v;
    v.reserve(1'000'000);
    // ... fill ...
    return v;                  // keine teure Kopie: NRVO oder Move
}

auto data = make_data();       // Ergebnis wird direkt übernommen

Große Objekte können sicher per Wert zurückgegeben werden. Der Compiler vermeidet Kopien durch Copy Elision / NRVO oder nutzt einen günstigen Move.

  • Copy Elision seit C++17 bei Prvalues garantiert, kein temporäres Objekt
  • Bei lokalen Variablen wie return v; greift meist NRVO; sonst wird gemoved
  • Daher: kein out-Pointer nötig, einfach Return by value

NRVO: Named Return Value Optimization

Der Compiler kann eine benannte lokale Variable direkt im Speicher des Rückgabewerts erzeugen. Dadurch entfällt die Kopie beim return.

std::vector<int> make_data() {
    std::vector<int> v;        // v ist eine benannte lokale Variable
    v.push_back(1);
    v.push_back(2);
    return v;                  // NRVO möglich
}

auto data = make_data();       // data wird direkt als Rückgabewert aufgebaut

Faustregel beim Return lokaler Variablen:

return v;              // gut: NRVO möglich
return std::move(v);   // meist schlechter, kann NRVO verhindern

std::move beim Zurückgeben lokaler Variablen ist meist unnötig und blockiert die Optimierung.

Teil IV: Klassen, Vererbung & Polymorphismus

Klassen: von struct zu class

C-Struktur: Bündel von Variablen unter einem Namen. C++-Klasse: erweitert das Konzept um Funktionen als Member.

struct A;      // Deklaration

struct A {     // Definition
    int  x;    // Datenmember (Feld)
    void f();  // Funktionsmember (Methode)
};
class A;       // Deklaration

class A {      // Definition
    int  x;    // Datenmember, hier: private
    void f();  // Funktionsmember, hier: private
};
  • struct und class sind technisch gleichwertig. Einziger Unterschied: Default-Zugriff (public bzw. private).
  • Konvention: struct für passive Objekte (reiner Datensatz), class für aktive Objekte (Datenabstraktion mit Invarianten).
  • RAII in einem Satz: Ressource im Konstruktor holen, im Destruktor freigeben, Lebensdauer = Objektlebensdauer. Details in Teil V.
  • Quelle: dieser Block ist eine Übersetzung von Federico Busato, „Modern C++ Programming“, Kapitel 8 (Object-Oriented Programming I), gekürzt und an unser Deck angepasst.
  • Für Umsteiger: Java/C# kennen nur class. Dass struct in C++ dasselbe kann (Methoden, Konstruktoren, Vererbung), überrascht viele. Der Unterschied zu C#-struct (Werttyp vs. Referenztyp) existiert in C++ nicht, alle Klassen sind Werttypen.
  • Konvention aus den Core Guidelines (C.2): struct, wenn die Member unabhängig variieren dürfen; class, sobald eine Invariante zu schützen ist.
  • RAII hier nur nennen, nicht vertiefen. Teil V macht es ausführlich. Implikation für Umsteiger: C++ braucht keinen Garbage Collector, aber du bist für Ressourcen verantwortlich.

Klassen: Member definieren und benutzen

Inline oder außerhalb definieren

struct A {
    void g();              // nur Deklaration

    void f() {             // Deklaration und
        std::cout << "f";  // Inline-Definition
    }
};

void A::g() {              // Definition außerhalb
    std::cout << "g";      // (typisch: in der .cpp)
}

Zugriff über den Punkt

struct B {
    void g() { std::cout << "g"; }
};

struct A {
    int  x;                  // Datenmember
    B    b;                  // Datenmember (Objekt)
    void f() { std::cout << "f"; }
};

A a;
a.x;      // Feld
a.f();    // Methode
a.b.g();  // Methode des Members
  • A::g(): der Scope-Operator sagt dem Compiler, zu welcher Klasse die Funktion gehört. Das ist der Normalfall bei Header/Source-Trennung: Deklaration in a.h, Definition in a.cpp.
  • Inline im Klassenkörper ist implizit inline, gut für kurze Getter. Lange Methoden gehören in die .cpp, sonst wird jeder Include teuer und jede Änderung löst Neubau aus.
  • Objekte als Member (B b;): in Java/C# wäre b eine Referenz, die erst null ist. In C++ liegt b im Objekt a, wird mit a gebaut und mit a zerstört.
  • Kein new nötig: A a; reicht, Objekt auf dem Stack. Auch das ist für Umsteiger neu.

Vererbung: Basisklasse und abgeleitete Klasse

Abgeleitete Klasse (Derived, Child): erbt Variablen und Funktionen einer anderen Klasse. Basisklasse (Base, Parent): die nächste Klasse, die diese Member bereitstellt.

Eine Ableitung behält alle Eigenschaften der Basis und fügt hinzu, sie kann nie etwas entfernen.

struct A {              // Basisklasse
    int value = 3;
    void g() {}
};

struct B : A {          // B ist von A abgeleitet ("B erweitert A")
    int data = 4;       // B erbt value und g() von A
    int f() { return data; }
};

A a;
B b;
a.value;                // 3
b.g();                  // geerbt von A
b.value;                // ebenfalls geerbt: 3

Syntax: class Derived : [Zugriffsattribut] Base { ... };

  • Vokabular festnageln: Basis/abgeleitet, Base/Derived, Parent/Child, Superklasse/Subklasse, alles dasselbe.
  • „Nie entfernen“: eine Ableitung kann Member nicht wegnehmen, nur hinzufügen oder (später) überschreiben. Deshalb ist Vererbung eine Erweiterung, keine Einschränkung.
  • Java/C#-Brücke: extends bzw. : BaseClass entspricht : public A. Das Zugriffsattribut kommt in zwei Folien.
  • struct B : A: bei struct ist die Vererbung per Default public, bei class per Default private. Das ist der Grund, warum wir bei class immer : public hinschreiben.

Vererbung: Ableitung als Basis verwenden

struct A {};
struct B : A {};

void f(A a) {}       // Kopie
void g(B b) {}       // Kopie

void f_ref(A& a) {}  // Referenz, gleiches gilt für A*
void g_ref(B& b) {}  // Referenz, gleiches gilt für B*

A a;
B b;
f(a);        // ok, ebenso f(b), f_ref(a), f_ref(b), g_ref(b)
g(b);        // ok, ebenso g_ref(b), aber NICHT g(a), g_ref(a)

A a1 = b;    // ok, auch A& a2 = b   (ein B "ist ein" A)
// B b1 = a; // Compilerfehler: ein A ist kein B

Ein B darf überall stehen, wo ein A erwartet wird. Umgekehrt nicht.

  • Liskov in einer Zeile: die Ableitung ist überall einsetzbar, wo die Basis erwartet wird. Das ist der Kern von „is-a“.
  • f(b) per Kopie: funktioniert, kopiert aber nur den A-Anteil von b. Das ist die Slicing-Falle, die wir später eigens anschauen. Per Referenz (f_ref(b)) passiert das nicht.
  • B b1 = a: der Compiler weiß nicht, was er für die zusätzlichen Member von B einsetzen soll. Konvertierung nach „unten“ gibt es nur explizit (Cast), und auch dann nur, wenn wirklich ein B dahintersteckt.

Zugriffsspezifizierer: public, protected, private

Ziel: direkten Zugriff auf die interne Darstellung verhindern, damit Objekte nicht in einen inkonsistenten Zustand geraten (Zugriffskontrolle).

Spezifizierer Wer darf zugreifen?
public alle: Methoden, abgeleitete Klassen, Code außerhalb der Klasse
protected Methoden der Klasse und abgeleitete Klassen
private nur Methoden der Klasse selbst (intern) 
struct A1 {
    int value;          // public (Default bei struct)
protected:
    void f1() {}        // protected
private:
    void f2() {}        // private
};
struct B : A1 {
    void h1() { f1(); }     // ok, f1 ist in B sichtbar
    // void h2() { f2(); }  // Fehler: f2 ist privat in A1
};

A1 a;
a.value;   // ok
// a.f1(); // Fehler: protected
// a.f2(); // Fehler: private
  • Abschnitte, nicht Attribute: in C++ gilt ein Spezifizierer ab seiner Zeile bis zum nächsten. Java/C# schreiben private vor jedes Member, C++ gruppiert. Reihenfolge-Konvention: erst public (Schnittstelle), dann protected, dann private.
  • Default: struct startet public, class startet private. Sonst kein Unterschied.
  • Wann public-Datenmember? Wenn sie sich jederzeit unabhängig ändern dürfen (reiner Datensatz, struct Point { int x, y; }). Wann private? Sobald sie nicht Teil der logischen Schnittstelle sind oder eine Invariante schützen (Größe muss zum Puffer passen, Zeiger muss const-correct bleiben).
  • protected sparsam: koppelt Ableitungen an die Implementierung der Basis. Getter/Setter sind oft die bessere Wahl.

Zugriff bei Vererbung: : public, : protected, : private

Das Attribut hinter dem Doppelpunkt legt fest, wie sichtbar die geerbten Member in der Ableitung sind:

Member in der Basis : public : protected : private
public public protected private
protected protected protected private
private unzugänglich unzugänglich unzugänglich 
struct A {
    int var1;      // public
protected:
    int var2;      // protected
};

struct B : protected A {
    int var3;      // public
};

B b;
// b.var1;  // Fehler: in B protected
// b.var2;  // Fehler: in B protected
b.var3;     // ok
class A {
public:
    int var1;
protected:
    int var2;
};

class B1 : A {};         // private-Vererbung!
class B2 : public A {};  // public-Vererbung

B1 b1;
// b1.var1;  // Fehler: in B1 private
B2 b2;
b2.var1;     // ok: in B2 public
  • Die Tabelle liest sich so: die Vererbungsart ist eine Obergrenze. : public lässt alles, wie es ist, : protected drückt public auf protected, : private drückt alles auf private. private in der Basis bleibt immer unzugänglich, egal wie geerbt wird.
  • Häufigster Fehler bei Umsteigern: class B1 : A {} ohne public. Dann ist die Vererbung privat, und A& a = b1; geht von außen nicht mehr. Symptom: „cannot convert B1 to A, inaccessible base“. Fix: : public schreiben. Immer.
  • Wann : private? Implementierungs-Vererbung („implemented-in-terms-of“), also Wiederverwendung ohne „is-a“. In modernem C++ nimmt man dafür Komposition (kommt am Ende dieses Teils).
  • Java/C#: kennen nur public-Vererbung. Das ist auch in C++ der Normalfall, die anderen zwei sind Spezialfälle.

Konstruktor

Konstruktor (ctor): spezielle Memberfunktion, die beim Erzeugen einer Instanz läuft. Ziel: Initialisierung und Ressourcenbeschaffung. Syntax: T(...), gleicher Name wie die Klasse, kein Rückgabetyp.

  • Ein Konstruktor soll alle Datenmember initialisieren
  • Mehrere Konstruktoren mit unterschiedlichen Signaturen sind erlaubt (Überladung)
  • Jeder Konstruktor darf constexpr sein

Default-Konstruktor T(): Konstruktor ohne Argumente. Jede Klasse hat immer einen: implizit, explizit oder gelöscht.

struct A {
    A()    {}   // expliziter Default-Ctor
    A(int) {}   // benutzerdefiniert (nicht default)
};
struct A {
    int x = 3;  // impliziter Default-Ctor
};
A a{};          // ruft ihn auf, wie: A a;
  • „Immer einen Default-Ctor“: entweder der Compiler generiert ihn (implizit, wenn kein anderer Ctor da ist), du schreibst ihn (explizit), oder er ist gelöscht (dann geht A a; nicht). Gelöscht: z. B. sobald ein eigener Konstruktor da ist, oder bei Referenz-/const-Membern. Falle nebenbei: A a2(); ist eine Funktionsdeklaration, A a2{}; nehmen.
  • Impliziter Default-Ctor ist constexpr, kann also zur Compile-Zeit laufen. Nur nebenbei.
  • Java/C#-Brücke: dasselbe Konzept, aber C++ hat mehr Spezialfälle (Copy-Ctor, Move-Ctor), die kommen in Teil V (Rule of 3/5) und im Anhang Move-Semantik.

Initializer-List und In-Class-Initialisierung

Die Initializer-List initialisiert Datenmember oder ruft den Basis-Konstruktor auf, bevor der Konstruktor-Body läuft. (Nicht verwechseln mit std::initializer_list.)

struct A {
    int x, y;
    A(int x1) : x(x1) {}   // ": x(x1)" ist die Initializer-List
    A(int x1, int y1) :
        x{x1},             // Klammer-Variante
        y{y1} {}           // (C++11)
};

In-Class-Member-Initializer (C++11): Default direkt bei der Deklaration; ein Konstruktor darf ihn überschreiben.

struct A {
    int         x   = 0;
    const char* str = nullptr;
    A() {}                 // x und str sind definiert
    A(const char* s) : str{s} {}
};

const- und Referenz-Member müssen über Initializer-List oder In-Class-Initializer gesetzt werden:

struct A {
    int        x;
    const char y;          // muss initialisiert werden
    int&       z;          // muss initialisiert werden
    const int  w{4};       // oder In-Class (C++11)
    A() : x(3), y('a'), z(x) {}
};
  • Aus Teil I bekannt: Initializer-List statt Zuweisung im Body (Sensor-Beispiel). Hier die vollständige Regel: alles, was nicht in der Liste steht, wird vorher default-konstruiert, und im Body kannst du nur noch zuweisen.
  • In-Class-Initializer ist der beste Ort für Defaults: einmal hinschreiben, gilt für alle Konstruktoren. Core Guidelines C.45/C.48.
  • const/Referenz: Zuweisung im Body ist unmöglich (y = 'a' auf ein const char geht nicht), deshalb zwingend Initializer-List.
  • Referenz-Member sind in der Praxis selten und machen die Klasse nicht zuweisbar. Nur zeigen, nicht empfehlen.

Initialisierungsreihenfolge

Member werden in der Reihenfolge ihrer Deklaration initialisiert, nicht in der Reihenfolge der Initializer-List.

struct ArrayWrapper {
    int* array;
    int  size;

    ArrayWrapper(int user_size) :
        size{user_size},
        array{new int[size]} {}
        // FALSCH: array wird ZUERST initialisiert,
        // size ist da noch undefiniert
};

ArrayWrapper a(10);
std::cout << a.array[4];   // Speicherzugriffsfehler

Warning

Initializer-List in derselben Reihenfolge wie die Deklarationen schreiben. Compiler warnen bei Abweichung (-Wreorder, MSVC C5038).

  • Warum so? Der Destruktor zerstört in umgekehrter Deklarationsreihenfolge. Damit das immer passt, muss die Konstruktion der Deklaration folgen, egal was in der Liste steht.
  • Demo: -Wall (GCC/Clang) bzw. /W4 plus C5038 (MSVC) anschalten, die Warnung „member initializer list order“ zeigen. Das ist genau der Grund, warum Warnungen als Fehler in CI Sinn ergeben.
  • Fix hier: size vor array deklarieren, oder besser: std::vector<int> data; nehmen, dann gibt es keinen rohen Zeiger mehr.

Uniform Initialization für Objekte

Uniform Initialization {} (C++11, auch List-Initialization): jedes Objekt gleich initialisieren, unabhängig vom Typ.

Vorteil: weniger redundante Typnamen bei Argumenten und Rückgabewerten.

struct Point {
    int x, y;
    Point(int x1, int y1) : x(x1), y(y1) {}
};

C++03

Point add(Point a, Point b) {
    return Point(a.x + b.x, a.y + b.y);
}
Point c = add(Point(1, 2), Point(3, 4));

C++11

Point add(Point a, Point b) {
    return { a.x + b.x, a.y + b.y };  // hier
}
auto c = add({1, 2}, {3, 4});         // hier
  • Aus Teil I bekannt ({} bei Variablen), hier die Objekt-Seite: return {…} und f({…}) bauen das Objekt aus dem erwarteten Typ. Spart Tipparbeit und ändert sich automatisch mit, wenn die Signatur wechselt.
  • Vorsicht bei explicit: return {1, 2} geht nicht, wenn der Konstruktor explicit ist (wie explicit Circle(double r) gleich auf der nächsten Folie). Dann return Point{1, 2};.
  • Überleitung: Klassen, Vererbung, Zugriff, Konstruktoren sitzen. Was noch fehlt, ist das eine Schlüsselwort, das Vererbung erst polymorph macht: virtual. Nächste Folie.
  • Narrowing: {} verbietet verengende Konvertierungen (Point p{1.5, 2} ist ein Fehler), das ist gewollt.

Klassische Klassenhierarchie: Runtime-Polymorphie

Polymorphie: Gemeinsames Interface in der Basisklasse, konkretes Verhalten in abgeleiteten Klassen.

#include <numbers>

class Shape {
public:
    virtual ~Shape() = default;            // wichtig bei Vererbung
    virtual double area() const = 0;       // pure virtual -> abstrakte Klasse
    virtual void   draw() const { /* default */ }  // optionale Default-Impl.
};

class Circle : public Shape {
public:
    explicit Circle(double r) : r_{r} {}
    double area() const override { return std::numbers::pi * r_ * r_; }
    void   draw() const override { /* ... */ }
private:
    double r_;
};
  • Polymorphie-Definition: Schnittstelle in der Basisklasse, Verhalten in den Ableitungen, das ist der Klassiker aus Java/C#.
  • virtual ~Shape() = default;: wichtigster Punkt, oft vergessen. Ohne virtuellen Destruktor wird beim delete shape* nur der Shape-Destruktor aufgerufen → Memory Leak in der Ableitung.
  • = 0 (pure virtual): Shape ist abstrakt, kann nicht instanziiert werden. Erzwingt, dass jede Ableitung area() selbst implementiert.
  • draw() mit Default-Implementierung: Punkt, dass virtuelle Methoden auch eine Standard-Implementierung haben können. Ableitungen können sie übernehmen oder überschreiben.
  • override: verpflichtende Markierung für Umsteiger. Compiler prüft, dass die Signatur wirklich passt. Tippfehler wie Area() statt area() werden sofort gefangen.
  • std::numbers::pi statt M_PI: moderner Header <numbers> (C++20). M_PI ist eine POSIX-Erweiterung, nicht standardisiert (MSVC kennt es nur mit _USE_MATH_DEFINES).
  • Was zeigen: Sensor-/Logger-/Shape-Hierarchie ist überall, std::ostream, std::exception, GUI-Frameworks.

Klassenhierarchie: Spielregeln

Regel Warum?
virtual ~Shape() = default; Sicheres Löschen über Shape* oder std::unique_ptr<Shape>
= 0 Macht eine Methode rein virtuell: abgeleitete Klassen müssen sie implementieren
Abstrakte Klasse Entsteht, sobald mindestens eine Methode rein virtuell ist
override Compiler prüft, ob wirklich eine Basismethode überschrieben wird
final Verhindert weiteres Überschreiben oder Ableiten

Eine polymorphe Basisklasse braucht einen virtuellen Destruktor. Rein virtuelle Methoden definieren verpflichtende Schnittstellen. override und final machen Vererbung sicherer und eindeutiger.

  • virtual ~Shape() = default;: Demo-Tipp: Ohne virtual ein delete shape* zeigen. In Visual Studio den Leak sichtbar machen: Debug-Build, am Anfang von main() _CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF); (Header <crtdbg.h>) → beim Programmende erscheint „Detected memory leaks!“ im Ausgabefenster. Alternativ MSVC-Warnung C4265 aktivieren (/w34265): „class has virtual functions, but its non-trivial destructor is not virtual“. Wirkt in der Demo gut.
  • = 0: wichtig zu betonen: macht die Klasse abstrakt. Shape s; geht nicht mehr. Nur via Ableitung instanziierbar.
  • Abstrakte Klasse: entsteht „automatisch“, sobald eine Methode rein virtuell ist. Man muss nicht extra abstract class schreiben (gibt’s nicht in C++).
  • override: formal optional, aber Core Guidelines empfehlen es immer zu setzen. Schützt vor Signatur-Drift bei Refactorings.
  • final: zwei Bedeutungen: auf Klasse → keine weitere Ableitung; auf Methode → kein weiteres Override. Erlaubt dem Compiler Devirtualisierung (Performance-Win).
  • Statement unten fasst die drei wichtigsten Punkte zusammen, die kann man auswendig sagen.

Klassenhierarchie: Verwendung

std::unique_ptr<Shape> s = std::make_unique<Circle>(2.0);

double a = s->area();   // ruft Circle::area() auf
s->draw();              // ruft Circle::draw() auf

Obwohl s den statischen Typ std::unique_ptr<Shape> hat, zeigt es tatsächlich auf ein Circle-Objekt. Virtuelle Methoden wie area() und draw() werden deshalb zur Laufzeit an die passende Implementierung der tatsächlichen Klasse weitergeleitet.

Der Aufruf wird zur Laufzeit an die richtige Methode des tatsächlichen Objekttyps gebunden, typischerweise über eine vtable.

Note

std::numbers::pi statt M_PI: M_PI ist nicht standardisiertes C++. Seit C++20 gibt es std::numbers::pi aus <numbers>.

  • Statischer vs. dynamischer Typ: Schlüsselbegriff. Statisch = was im Quellcode steht (unique_ptr<Shape>); dynamisch = worauf zur Laufzeit gezeigt wird (Circle).
  • s->area(): auch wenn s formal nur Shape kennt, ruft das die Circle::area() auf. Hier den Aha-Moment laufen lassen.
  • vtable-Hinweis: nur erwähnen, nicht vertiefen. „Compiler legt eine Tabelle pro Klasse mit Funktionszeigern an, jedes Objekt hat einen Pointer dorthin.“ Reicht für die Schulung. (Im VS-Debugger sieht man den __vfptr im Watch-Fenster, eine nette Live-Demo.)
  • make_unique statt new, hier zum ersten Mal in dieser Form. Smart Pointer kommen in Teil VI ausführlich, aber so sieht man sie schon mal.
  • Demo-Idee: Ein Circle und ein Square in derselben vector<unique_ptr<Shape>> und total += s->area(); durchlaufen (Projekt 05_vererbung).

Polymorphismus: dynamischer Dispatch

std::vector<std::unique_ptr<Shape>> shapes;

shapes.push_back(std::make_unique<Circle>(1.0));
shapes.push_back(std::make_unique<Square>(2.0));

double total = 0.0;
for (const auto& s : shapes) {
    total += s->area();   // virtueller Aufruf -> konkrete Implementierung
}

Dynamischer Dispatch: Obwohl s nur als Shape bekannt ist, wird bei area() zur Laufzeit die Methode der konkreten Form aufgerufen.

Container speichert Shape-Zeiger, die echten Objekte sind Circle, Square, … Durch virtual ruft s->area() automatisch Circle::area() bzw. Square::area() auf.

  • Klassisches Pattern: heterogener Container, also verschiedene konkrete Typen mit gemeinsamer Basisklasse.
  • Warum unique_ptr und nicht vector<Shape>? Slicing! (kommt nächste Folie). vector<Shape> würde nur den Shape-Anteil speichern, der Rest wird abgeschnitten.
  • Range-for mit const auto&: wie immer Default. Iterator wäre vector<unique_ptr<Shape>>::const_iterator, mit auto ist’s lesbar.
  • Performance-Hinweis: virtuelle Aufrufe haben Kosten (1 Pointer-Indirektion). In Hot-Loops wo’s drauf ankommt: lieber Templates / std::variant. Aber 99% der Fälle: kein Problem.
  • Vergleich Java/C#: dort ist polymorpher Dispatch der Default, alle Methoden sind virtuell, außer du markierst sie als final/sealed. C++ ist umgekehrt: Default nicht-virtuell, opt-in mit virtual.

Slicing-Falle

void process(Shape s);        // by value → SLICING!
Circle c{1.0};
process(c);                   // kopiert nur den Shape-Teil

void process(const Shape& s); // ✓ richtig: kein Slicing, polymorph

Merke: Polymorphe Objekte nie by value übergeben, nur per Referenz oder Smart Pointer.

  • Slicing erklären: Shape s legt ein echtes Shape-Objekt auf den Stack an. Wenn du Circle c reinkopierst, werden nur die Shape-Member kopiert, der Circle-Anteil (z. B. r_) wird abgeschnitten.
  • Konsequenz: s.area() würde den abstrakten Shape::area() aufrufen wollen, was bei reinem virtual gar nicht geht (Compile-Fehler) oder den Default-Shape-Algorithmus aufruft (falscher Wert).
  • Lösung: const Shape& oder Shape* oder unique_ptr<Shape>. Referenz/Pointer behalten den dynamischen Typ.
  • Einer der häufigsten Fehler bei Java/C#-Umsteigern, weil dort alle Objekte automatisch by-reference sind. In C++ musst du es explizit machen.
  • Demo-Idee: Lass eine Funktion void process(Shape s) einen Circle nehmen und s.area() aufrufen, bei abstraktem Shape gibt’s Compile-Fehler, das beweist das Slicing. Mit konkreter Basis (Animal/Dog in 05_vererbung) sieht man das falsche Verhalten zur Laufzeit.

Mehrfachvererbung & das Diamantenproblem

C++ erlaubt Mehrfachvererbung: eine Klasse kann mehrere direkte Basisklassen haben. Das ist mächtig, kann aber zu Mehrdeutigkeit führen.

class Vehicle { public: int mass() const; };

class Land : public Vehicle { /* ... */ };
class Air  : public Vehicle { /* ... */ };

class AirCar : public Land, public Air { /* ... */ };   // Diamant!

AirCar bond;
bond.mass();          // ✗ ambiguous: welcher Vehicle? Land::Vehicle oder Air::Vehicle?
bond.Land::mass();    // ✓ explizite Auflösung mit Scope-Operator
        Vehicle    Vehicle           ← zwei separate Vehicle-Anteile!
          ▲          ▲
          │          │
         Land       Air
            ▲      ▲
             ╲    ╱
              AirCar

Diamantenproblem: zwei Wege von AirCar führen zu Vehicle → AirCar enthält den Vehicle-Teil doppelt. Code, Daten und Konstruktor-Aufrufe werden mehrdeutig.

  • Mehrfachvererbung in C++ erlaubt: anders als Java/C#. Mit Macht kommt Verantwortung.
  • AirCar-Beispiel ist klassisch und stammt aus Stroustrup. Auto + Flugzeug (James Bond / The Man with the Golden Gun).
  • Compile-Fehler bei bond.mass(): Compiler weiß nicht, welchen Vehicle-Anteil. Beide Pfade sind gleich gültig.
  • Workaround mit Scope-Operator funktioniert, ist aber unschön, der Aufrufer muss wissen, dass es überhaupt zwei gibt.
  • Datenproblem nicht vergessen: AirCar hat zwei mass-Felder, doppelter Speicher, doppelter Konstruktor-Aufruf für Vehicle.
  • ASCII-Diagramm zeigen und das „Diamant“-Wort durch Zeichnen begründen, der Anfang ist gemeinsam, dann teilt’s sich, dann läuft’s wieder zusammen.
  • Wichtiger Punkt: der Diamant entsteht automatisch, sobald zwei Basisklassen die gleiche Großmutter haben. Nicht nur bei expliziter Mehrfachvererbung.

Virtuelle Vererbung: Lösung in C++

virtual bei der Vererbung sorgt dafür, dass die gemeinsame Basisklasse nur einmal im Endobjekt existiert, der Diamant wird zur Raute.

class Vehicle { public: int mass() const; };

class Land : public virtual Vehicle { /* ... */ };      // ← virtual
class Air  : public virtual Vehicle { /* ... */ };      // ← virtual

class AirCar : public Land, public Air { /* ... */ };

AirCar bond;
bond.mass();          // ✓ eindeutig, nur ein Vehicle im Objekt
  • Konstruktor-Sonderregel: virtueller Basis-Konstruktor wird vom konkretesten Typ aufgerufen, Land/Air reichen ihn nicht durch
  • Pragmatik: in modernem C++ selten gebraucht, bevorzuge Komposition oder Interface-Klassen (nur reine virtuelle Methoden)
  • Java/C# kennen keinen Diamanten: Single-Inheritance + mehrere Interfaces schließen ihn strukturell aus
  • virtual an der Vererbung, nicht an einer Methode: Schlüsselwort wird hier in einer dritten Bedeutung benutzt (neben virtual void f() und virtual ~T()).
  • Effekt im Speicher-Layout: statt zwei Vehicle-Anteile nur einen. Der Compiler legt eine zusätzliche Indirektion an, um beide Pfade auf denselben Vehicle zu zeigen.
  • Konstruktor-Sonderregel ist die Falle: bei normaler Vererbung würde Land(int x) : Vehicle(x) reichen. Bei virtual reicht AirCar selbst den Vehicle-Konstruktor durch, Land und Air ignorieren den.
  • Pragmatik-Bullet ernst nehmen: in moderner Codebasis trifft man virtuelle Vererbung selten. Die Standard-Bibliothek iostream ist eines der wenigen Beispiele (Diamant basic_istream/basic_ostream/basic_iostream).
  • Java/C#-Vergleich beruhigt Umsteiger, sie haben das Problem nie gesehen, weil ihre Sprache es ausschließt.
  • Wenn du es nicht brauchst: weiter zur nächsten Folie (Komposition).

Komposition statt Vererbung: „has-a“ statt „is-a“

Vererbung drückt aus: „X ist ein Y“ (Car ist ein Vehicle). Komposition drückt aus: „X hat ein Y“ (Car hat einen Engine). Komposition ist meist die flexiblere und einfachere Wahl.

Vererbung („is-a“)

class Vehicle { /* ... */ };

class Car : public Vehicle {
    // erbt alles von Vehicle,
    // kann Methoden überschreiben
};

Kopplung Basis ↔︎ Ableitung ist eng. Polymorphie nötig? Sonst zu mächtig.

Komposition („has-a“)

class Engine { /* ... */ };

class Car {
    Engine engine_;       // hat einen Engine
    Wheels wheels_[4];    // hat vier Räder
};

Schwächere Kopplung: Member austauschbar. Funktioniert ohne virtual/Hierarchie.

  • Faustregel: bevorzuge Komposition, außer du brauchst echte Polymorphie über Basisklassen-Zeiger (Core Guidelines C.121)
  • Mehrere „Rollen“ statt Mehrfachvererbung: einzelne Member halten, kein Diamant. Gleiche Empfehlung in Java/C# (favor composition over inheritance).
  • „is-a“ vs „has-a“ ist die Schlüssel-Frage beim Modellieren, vor jeder Klasse stellen.
  • Vererbungs-Beispiel: Car : Vehicle passt, ein Auto IST ein Fahrzeug. Aber Car : Engine wäre falsch, ein Auto IST kein Motor, es hat einen.
  • Komposition-Beispiel: Der Engine ist Member, kann jederzeit ausgetauscht werden (Setter, Konstruktor). Bei Vererbung müsste man eine neue Klasse ableiten.
  • Kopplung: Vererbung kettet die Ableitung an alle Implementierungsdetails der Basisklasse, auch private. Komposition exponiert nur die Public-API des Members.
  • Core Guidelines C.121 explizit erwähnen, eine der wichtigsten Faustregeln im modernen C++.
  • Java/C#-Brücke: „favor composition over inheritance“, Effective Java Item 18, ein Klassiker.
  • Wann doch Vererbung? Wenn du polymorph über Basisklassen-Zeiger zugreifen willst (heterogene Container, Strategy-Pattern), oder wenn die Ableitung wirklich substituierbar sein soll (Liskov-Prinzip).

Interface-Klassen: Java/C#-Interfaces in C++

Eine Interface-Klasse ist eine abstrakte Klasse, die nur reine virtuelle Methoden und keine Daten enthält, das C++-Pendant zu Java-/C#-interface. Mehrfachvererbung davon ist kein Diamant (keine Daten doppelt).

class Drawable {                                      // Interface, nur Methoden
public:
    virtual ~Drawable() = default;
    virtual void draw() const = 0;                    // = 0 → muss überschrieben werden
};

class Serializable {
public:
    virtual ~Serializable() = default;
    virtual std::string to_json() const = 0;
};

class Sensor : public Drawable, public Serializable { // mehrere "Rollen", sicher
public:
    void        draw()    const override { /* zeichnen */ }
    std::string to_json() const override { return /* ... */; }
};
  • Konvention: in C++ oft mit Suffix *able, I* oder im interface::-Namespace
  • Klassischer Einsatz: Plugins, Strategy-Pattern, austauschbare Implementierungen (z. B. Datei- vs. Netzwerk-Logger)
  • Wichtig: C++ hat kein interface-Schlüsselwort. Ein Interface ist nur eine Konvention: abstrakte Klasse mit ausschließlich = 0-Methoden und keinen Daten.
  • Beide Klassen mit virtual ~Drawable() = default;: kritisch für Polymorphie.
  • Sensor : public Drawable, public Serializable: Mehrfachvererbung von Interfaces ist safe, weil keine Daten kollidieren können.
  • Kein Diamant, weil: beide Interfaces haben keine gemeinsame Basis mit Daten. Selbst wenn sie eine hätten: solange keine Daten doppelt sind, gibt’s nichts zum Verdoppeln.
  • override an jeder implementierenden Methode: Compiler prüft Signatur.
  • Naming-Konvention: Drawable, Hashable, Comparable (*able-Suffix wie in Rust-Traits) oder IShape, IDrawable (Hungarian-Style aus C# / COM).
  • Brückenschlag zu Java/C#: das ist die gleiche Idee, nur dass dort die Sprache das Konzept fest verankert; in C++ machst du’s mit den vorhandenen Mitteln (abstrakte Klassen).

Teil V: Dynamische Speicherverwaltung

Stack vs. Heap: wo liegt was?

Stack Heap
Lebenszeit an Scope gebunden ({ ... }) bis die Ressource freigegeben wird
Freigabe automatisch beim Verlassen des Scopes manuell (delete) oder automatisch durch RAII / Smart Pointer
Allokation automatisch für lokale Variablen dynamisch zur Laufzeit (new, make_unique, Container, …)
Geschwindigkeit sehr schnell tendenziell langsamer
Größe begrenzt, pro Thread (Windows: 1 MB, Linux: ~8 MB) deutlich größer, pro Prozess
Thread-Sicht jeder Thread hat seinen eigenen Stack gemeinsam genutzt von allen Threads
Bei Überlauf Stack-Overflow → meist Crash Allokation kann fehlschlagen → std::bad_alloc

Faustregel: Lokale Objekte stack-nah halten. Heap verwenden, wenn Objekte groß sind, polymorph gespeichert werden oder ihre Lebenszeit den aktuellen Scope überdauern muss.

  • Mentales Modell aufbauen: Stack = LIFO, sehr schnell, Compile-Zeit-Größe. Heap = Free-List, Laufzeit-Größe, deutlich teurer.
  • Lebenszeit/Freigabe bewusst getrennt: bei Stack ist beides automatisch und gekoppelt; bei Heap ist Freigabe separate Aktion, die schiefgehen kann.
  • „Manuell oder durch RAII“ ist der Schlüsselbegriff und nimmt vorweg, dass Smart Pointer eine reguläre Form der Freigabe sind.
  • Größenordnungen merken: Windows 1 MB (MSVC-Default, Linker-Option /STACK), Linux 8 MB pro Thread. Bei tiefen Rekursionen oder großen lokalen Arrays → Stack-Overflow.
  • Heap pro Prozess (geteilt): wichtig für Thread-Programmierung später (Synchronisierung).
  • Bei Überlauf: Stack crasht sofort und still (Hardware-Trap), Heap wirft std::bad_alloc (oder nullptr bei malloc).
  • Demo-Idee: int big[1'000'000]; als lokale Variable (4 MB > 1 MB) → Visual Studio meldet „Unhandled exception: Stack overflow“ direkt an der Zeile. Dasselbe als std::vector<int> big(1'000'000); → läuft (Heap).

Heap ist nicht böse: RAII übernimmt

Modernes C++ heißt nicht „Heap vermeiden um jeden Preis“. Wichtig ist: Ownership sauber kapseln. Der Heap ist okay, solange RAII die Freigabe übernimmt.

void f() {
    std::vector<int> v(1'000'000);          // 1 Mio Ints
    // ...
}                                           // Cleanup automatisch

Was hier wirklich passiert:

Bestandteil Liegt auf … Aufräumen durch …
v-Objekt selbst Stack Compiler beim Scope-Ende
v-Elemente (1 Mio) Heap ~vector() ruft delete[] auf

→ Heap-Nutzung ist deterministisch und exception-safe, ohne dass du new/delete schreibst.

Schlussregel: Niemals rohes new/delete. Nutze automatische Variablen, STL-Container und Smart Pointer, dann ist Cleanup deterministisch und exception-safe.

  • Diese Folie ist die wichtigste Botschaft des ganzen Teils V: nicht „Heap böse“, sondern „Ownership richtig“.
  • std::vector<int> v(1'000'000);: sehr konkretes Beispiel, das Java/C#-Umsteiger gut verstehen. Eine Mio Ints sind Heap-Speicher, aber du musst nichts aufräumen.
  • Die Tabelle aufschlüsseln: Das v-Objekt (Header mit Pointer, Size, Capacity) liegt auf dem Stack (drei Pointer/Größen, ~24 Byte). Die eigentlichen Daten (1 Mio × 4 Byte = ~4 MB) liegen auf dem Heap.
  • ~vector() wird automatisch aufgerufen und ruft intern delete[] auf den internen Pointer auf. Du siehst delete[] nirgends in deinem Code.
  • Exception-safe: auch bei Wurf zwischen Konstruktion und Scope-Ende läuft ~vector() zuverlässig (Stack-Unwinding).
  • Bedeutung für Umsteiger: Java hat GC, C# hat GC, Python hat refcount+GC. C++ hat deterministisches Aufräumen via RAII, beim Scope-Ende, garantiert sofort, keine GC-Pausen.
  • Schlussregel betonen: wir lernen new/delete jetzt zwar gleich (nächste Folie), aber selber schreiben tust du das in modernem Code praktisch nie.

new / delete: die Mechanik

new T(args) macht zwei Dinge auf einmal: Speicher reservieren und Objekt konstruieren. delete macht beide rückwärts.

int* p   = new int{42};                   // Heap-Speicher + int-Init
delete p;

int* arr = new int[100];                  // 100 ints
delete[] arr;                             // ⚠ [] nicht vergessen!

Sensor* s = new Sensor{"temp-1", 30.0};   // ruft Konstruktor auf
delete s;                                 // ruft Destruktor auf, gibt Speicher frei

new/delete vs. C-malloc/free: new ruft den Konstruktor, ist typsicher (liefert T* statt void*), kennt sizeof(T) selbst und wirft std::bad_alloc statt nullptr zurückzugeben.

Kardinalsünden (alle = Undefined Behavior): new mit free mischen · new[] mit delete · delete zweimal · Pointer überschreiben vor delete

  • new macht zwei Dinge: Speicher reservieren UND Konstruktor aufrufen. delete macht beide rückwärts: Destruktor aufrufen UND Speicher freigeben.
  • Single vs. Array: new T vs. new T[n], die Symmetrie zu delete T und delete[] T ist hart, Vermischung = UB.
  • Konstruktor-Aufruf: new Sensor{"temp-1", 30.0} ruft den Sensor-Konstruktor mit den Args auf. Das ist der Hauptunterschied zu malloc.
  • malloc/free-Vergleich: Wer aus C kommt, kennt das. Wichtig: niemals mischen, sonst UB.
  • Typsicher: new int gibt int* zurück, malloc gibt void*. In C++ braucht malloc einen Cast, den schreibt niemand mehr.
  • std::bad_alloc vs. nullptr: new wirft, malloc gibt nullptr zurück. Ein if (!p) nach new macht keinen Sinn, die Exception ist schon weg.
  • Die vier Kardinalsünden sind alles Undefined Behavior, kein Compile-Fehler, oft kein Laufzeit-Fehler, sondern Crash oder Datenkorruption irgendwo später.
  • Ausblick: Genau diese Probleme behandeln die nächsten Folien (Falle 2-5) konkret.

Memory Leak: was geht konkret schief?

void process() {
    int* data = new int[10'000];

    if (some_condition()) {
        return;                          // ⚠ data niemals freigegeben → LEAK
    }
    if (parse(data) < 0) {
        throw std::runtime_error{"x"};   // ⚠ Exception → kein delete → LEAK
    }
    delete[] data;                       // wird nur im Glücksfall erreicht
}

Definition: ein dynamisch allokierter Block, den das Programm nicht mehr erreichen kann, aber auch nicht freigegeben hat. Heap-Block bleibt belegt, niemand kennt mehr seine Adresse.

  • Ursache fast immer: unklares Ownership, Exception-Pfad nicht bedacht, mehrere Exit-Pfade
  • Tools: Visual Studio Diagnosetools (Arbeitsspeicher-Snapshots), CRT-Debug-Heap (_CrtDumpMemoryLeaks), AddressSanitizer (/fsanitize=address), Valgrind (Linux)
  • Lösung: RAII, Ressource an ein Stack-Objekt binden, das beim Scope-Ende automatisch freigibt
  • Beide Leak-Pfade durchgehen: Frühausstieg per return und Exception per throw. Beide springen am delete[] vorbei.
  • Typische Argumentation eines Programmierers: „Ich vergesse das delete schon nicht.“ Funktioniert das für jeden Pfad? Bei 5 Returns + 3 Exceptions = 8 Pfade. Bei 2 Ressourcen = 16 Pfade. Keine Chance.
  • Definition: „Block existiert noch, niemand kann ihn mehr ansprechen, niemand gibt ihn frei“. Das OS gibt den Speicher erst beim Programm-Ende zurück.
  • Konsequenz: kurzlebiges Programm verzeiht; bei Server, der monatelang läuft, sammelt sich’s bis OOM-Kill.
  • Tools demonstrieren (Visual Studio):
    • CRT-Debug-Heap: Debug-Build, am Anfang von main(): _CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF); (<crtdbg.h>). Beim Programmende steht „Detected memory leaks!“ mit Blockgröße im Ausgabefenster. Null Aufwand, wirkt in der Demo gut.
    • Diagnosetools: Debuggen → Fenster → Diagnosetools → Arbeitsspeicherauslastung: Snapshot vor/nach process(), Differenz zeigt den Block samt Allokations-Stack.
    • AddressSanitizer (/fsanitize=address): findet unter MSVC Overflow/Use-after-free, aber keine Leaks (kein LeakSanitizer unter Windows). Für Leaks also Debug-Heap nehmen.
    • Valgrind (valgrind --leak-check=full ./prog), nur Linux/macOS; kurz als Gegenstück erwähnen.
  • Cliffhanger: „Lösung kommt, RAII auf der nächsten Folie.“

Klassische Pointer-Fallen: Übersicht

Wenn du new/delete von Hand schreibst, lauern fünf klassische Fallen. Die ersten haben wir schon gesehen, jetzt kommen die anderen vier im Detail.

Falle Was geht schief?
Memory Leak (schon gesehen) Pointer überschrieben oder Funktion verlassen, ohne delete
Double-Free delete zweimal auf demselben Pointer aufgerufen
Dangling Pointer / Use-after-free Auf bereits freigegebenen Speicher zugreifen
delete vs. delete[] Array mit delete (oder umgekehrt) freigegeben
Exception-Safety Wurf zwischen new und delete → kein Cleanup

→ Gemeinsame Wurzel: Ownership ist im Code nicht sichtbar. Ein int* sagt nicht, wer freigeben muss.

  • Übersichts-Folie: Tabelle als Vorschau, jeder Eintrag bekommt nachher eine eigene Folie.
  • „5 Fallen“: die Zahl ist wichtig: zeigt, dass mit new/delete viele unabhängige Probleme dazukommen, nicht nur eines.
  • „Gemeinsame Wurzel: Ownership“: wichtigste Botschaft. Alle 5 Fallen entstehen, weil ein roher Pointer nicht ausdrückt, wer für die Freigabe verantwortlich ist.
  • Übergang vorbereiten: „Wir gehen jetzt jede einzeln durch, und zeigen am Ende, dass Smart Pointer/RAII alle 5 strukturell ausschalten.“
  • Memory Leak als ‘schon gesehen’ markiert: letzte Folie war dazu, jetzt kommen die anderen vier.

Falle 2: Double-Free

int* p = new int{42};
delete p;            // ✓ ok: Speicher freigegeben
delete p;            // ✗ DOUBLE-FREE: Undefined Behavior
                     //    typisch: Crash oder Heap-Korruption

Wie es im Alltag entsteht (geteiltes Ownership):

void process(int* data) {
    delete data;     // ⚠ Funktion löscht
}

int* p = new int{42};
process(p);
delete p;            // ✗ Double-Free: Funktion hatte schon delete aufgerufen

Klassisches Ownership-Problem: zwei Stellen denken, sie wären verantwortlich. unique_ptr löst das strukturell, es ist nicht kopierbar, nur einer kann freigeben.

  • Trivialfall zeigen: delete p; delete p;, sieht idiotisch aus, passiert aber häufiger als man denkt (z. B. Copy-Konstruktor vergessen, beide Kopien rufen delete auf).
  • Realistischer Fall: process(p) löscht intern, danach noch delete p; außen. Ist nicht offensichtlich falsch, wenn man die Funktion nicht kennt.
  • Warum so gefährlich: UB ≠ Crash. Es kann scheinbar funktionieren und erst Wochen später bei anderem Lauf-Pfad zum Heap-Korrupt-Crash führen.
  • Visual Studio Debug-Build fängt den Doppel-Free meist sofort: der Debug-Heap prüft beim zweiten delete seine Blockliste und meldet einen Assertion-Dialog („_CrtIsValidHeapPointer“ / „HEAP CORRUPTION DETECTED“). Im Release-Build dagegen: stiller Crash irgendwo später, genau der Unterschied, den man zeigen will.
  • unique_ptr-Lösung: kann nicht kopiert werden. Wer den unique_ptr per Wert nimmt, übernimmt den Besitz, der alte ist nullptr. Doppel-Delete strukturell unmöglich.
  • Pendant zu Rust: Borrow-Checker macht im Prinzip dasselbe, aber zur Compile-Zeit. C++ erreicht es per Konvention + Typ-System.

Falle 3: Dangling Pointer / Use-after-free

int* p = new int{42};
delete p;            // Speicher freigegeben
*p = 99;             // ✗ DANGLING POINTER: UB
                     //    p zeigt noch auf die Adresse,
                     //    aber sie gehört dir nicht mehr

Stack-Variante, Pointer auf eine lokale Variable zurückgeben:

int* make_value() {
    int x = 42;
    return &x;       // ✗ x stirbt am Funktions-Ende → dangling
}

int* p = make_value();
*p;                  // ✗ Use-after-free auf Stack-Speicher
  • Besonders fies: funktioniert manchmal (OS hat Block noch nicht recycelt) → schleichende Bugs in Produktion.
  • Defensiv: nach delete immer p = nullptr;, dann crasht’s sofort, nicht zufällig.
  • Strukturell: Smart Pointer + weak_ptr.lock() machen Use-after-free unmöglich.
  • Heap-Variante: Pointer überlebt seinen Speicher. delete p gibt frei, *p = 99 greift zu, auf etwas, das jetzt anderem gehört.
  • Stack-Variante: auch unbedingt zeigen. Junior-Falle Nr. 1: Pointer auf lokale Variable zurückgeben. &x ist nach Funktions-Ende Müll. MSVC warnt hier übrigens (C4172 „returning address of local variable“), Warnungen ernst nehmen!
  • *p ohne Zuweisung ist dasselbe Problem, auch nur Lesen ist UB.
  • „Funktioniert manchmal“: der schlimmste Modus von UB. AddressSanitizer macht aus dem „manchmal“ ein „immer schreiend“.
  • Demo-Idee (Projekt backup_c_sanitizers, Eingabe use-free): ohne ASan läuft es scheinbar durch („druckt 99“). Dann im Projekt AddressSanitizer aktivieren (C/C++ → Allgemein; Laufzeitprüfungen /RTC1 auf Standard) → Visual Studio hält an der Zeile mit „heap-use-after-free“ und zeigt den Stack der Allokation und des delete.
  • p = nullptr; Verteidigung: kein Wundermittel, andere Pointer auf dieselbe Adresse sind weiter dangling. Aber der konkrete p ist sicher.
  • weak_ptr.lock() vorbereiten, kommt in Teil VI als saubere Lösung.

Falle 4: delete vs. delete[]-Verwechslung

int* single = new int{42};
int* arr    = new int[100];

delete   single;     // ✓ Single-delete für Single-new
delete[] arr;        // ✓ Array-delete für Array-new

// Vertauscht:
delete   arr;        // ✗ UB: Array-Header nicht berücksichtigt
delete[] single;     // ✗ UB: versucht 100 Destruktoren auf einer Adresse

Warum es überhaupt zwei Operatoren gibt: new[] reserviert oft mehr Speicher als angefragt, vor dem Pointer steht meist die Anzahl der Elemente, damit delete[] weiß, wie viele Destruktoren es aufrufen muss.

Bei int (kein Destruktor) merkst du oft nichts. Bei eigenen Klassen → Crash oder Leak.

→ std::unique_ptr<T[]> und std::vector<T> machen es intern automatisch richtig.

  • Symmetrie betonen: new T ↔︎ delete T, new T[] ↔︎ delete[] T. Vertauschen = UB, immer.
  • Warum zwei Operatoren? Der Compiler legt bei new T[N] zusätzlichen Speicher VOR dem Pointer an, in dem die Anzahl steht. delete[] weiß so, wie viele Destruktoren es aufrufen muss.
  • Bei int (POD) merkt man den Fehler oft nicht, weil keine Destruktoren gerufen werden. Bei class Foo { ~Foo(); } aber sofort: delete arr ruft nur Destruktor[0] auf, der Rest ist Leak.
  • Lösung in modernem C++: std::unique_ptr<T[]> ist eine Spezialisierung mit delete[] als Default-Deleter. Aber eigentlich nimmt man std::vector<T>, schöner und mit Wachstum.
  • Faustregel: Wenn du new T[] schreiben willst, schreibe stattdessen std::vector<T>.

Falle 5: Exception-Safety, kein automatisches Cleanup

void process() {
    int* data = new int[10'000];

    risky_function();        // ⚠ wirft eine Exception

    delete[] data;           // ✗ wird NIE erreicht
}

Manueller Workaround mit try/catch:

void process() {
    int* data = new int[10'000];
    try {
        risky_function();
    } catch (...) {
        delete[] data;       // Cleanup im Exception-Pfad
        throw;               // weiterleiten
    }
    delete[] data;           // Cleanup im Erfolgs-Pfad
}

Bei zwei Ressourcen: vier Pfade. Bei drei: acht. Wartungs-Hölle. RAII löst das in null zusätzlichen Code-Zeilen, der Destruktor läuft immer.

  • Stack-Unwinding erklären: wenn eine Exception fliegt, „rollt“ der Stack nach oben. Auf jedem Frame werden die lokalen Objekte zerstört. Kein normaler Code dazwischen wird ausgeführt, das delete[] wird übersprungen.
  • try/catch-Workaround ist technisch korrekt, aber kombinatorisch explodiert: bei mehreren Ressourcen brauchst du verschachtelte try/catch oder Goto-Tricks.
  • 2 Ressourcen → 4 Pfade: Erfolg, Fehler-bei-erste-Ressource, Fehler-bei-zweite-Ressource, Fehler-bei-Hauptcode. Jeder muss richtig aufgeräumt werden.
  • 3 Ressourcen → 8 und so weiter. Mit jedem zusätzlichen new verdoppelt sich die Komplexität.
  • RAII-Ausblick: alle 5 Pfade laufen automatisch sauber, weil der Destruktor garantiert beim Verlassen des Scopes läuft, egal ob normal oder durch Exception. Das ist der Punkt der nächsten Folie.
  • Das ist die wichtigste Argumentations-Folie für RAII: gut zeitlich Raum lassen, das wirken zu lassen.

RAII: Das fundamentale Idiom

Resource Acquisition Is Initialization: Ressource im Konstruktor erworben, im Destruktor automatisch freigegeben.

class File {
public:
    explicit File(const char* path) : fp_{std::fopen(path, "r")} {
        if (!fp_) throw std::runtime_error{"cannot open file"};
    }
    ~File() { std::fclose(fp_); }                  // gültiges File ⇒ gültiges fp_

    File(const File&)            = delete;         // nicht kopierbar,
    File& operator=(const File&) = delete;         // sonst zwei fclose auf demselben FILE*
private:
    std::FILE* fp_;
};

Merksatz: RAII bindet die Lebensdauer einer Ressource an die Lebensdauer eines Objekts. Der Destruktor läuft beim Verlassen des Scopes, auch bei Exceptions.

So werden Dateien, Speicher, Locks, Sockets in modernem C++ verwaltet.

  • RAII = Resource Acquisition Is Initialization: der Name ist sperrig, gemeint ist: Ressource bei Konstruktion holen, bei Destruktion freigeben.
  • File-Beispiel: Konstruktor öffnet fopen, Destruktor schließt fclose. Wenn fopen fehlschlägt, fliegt eine Exception bevor das Objekt existiert → kein invalides File-Objekt entsteht.
  • MSVC-Hinweis: fopen löst Warnung C4996 („unsafe, use fopen_s“) aus, in den Schulungsprojekten per _CRT_SECURE_NO_WARNINGS abgeschaltet. Kurz erwähnen, damit niemand erschrickt.
  • Kein if (fp_) im Destruktor nötig: Konstruktor wirft bei Fehler, wenn das Objekt existiert, ist fp_ garantiert gültig.
  • Copy verbieten mit = delete: zwei Files würden fclose zweimal auf demselben Handle aufrufen → undefined behavior. Move kann man erlauben, ist aber hier weggelassen für Kürze.
  • Stack-Unwinding: der Mechanismus, der RAII zur Magie macht. Bei jeder Exception werden lokale Destruktoren in umgekehrter Reihenfolge aufgerufen.
  • STL nutzt RAII intern: vector, string, unique_ptr, lock_guard, ifstream, alle sind RAII-Wrapper.
  • Java/C# Pendant: try-with-resources / using, manuell pro Objekt, in C++ automatisch durch Sprache.
  • Demo-Idee: dasselbe process() aus Falle 5 mit std::ifstream und std::vector schreiben. 5 Zeilen Code, alle Pfade exception-safe.
  • Übungsblock hier: Projekt 06b_raii_uebung (ScopeGuard, Timer, TempFile, DynArray), Lösung 06b_raii_uebung_loesung.

Rule of 0 / 3 / 5

  • Rule of 0: wenn möglich keine Spezialmember selbst schreiben. Ressourcen über STL-Typen halten (std::vector, std::string, std::unique_ptr, …) → der Compiler erzeugt passende Konstruktoren, Zuweisungen und Destruktoren.

  • Rule of 3 (C++98): wenn eine Klasse eine dieser Funktionen selbst definiert, müssen meist alle drei betrachtet werden: Destruktor, Copy-Konstruktor, Copy-Assignment.

  • Rule of 5 (C++11): mit Move-Semantik kommen zwei weitere hinzu: Move-Konstruktor und Move-Assignment.

Bevorzugt Rule of 0. Nur Klassen, die direkt Ownership einer Ressource verwalten, sollten Destruktor, Copy- oder Move-Operationen selbst definieren.

  • Rule of 0 ist die wichtigste, heißt: nimm STL-Member, dann generiert der Compiler alle Spezialmember korrekt. Du schreibst keinen Konstruktor, keinen Destruktor, keine Copy/Move-Operationen.
  • Rule of 3 (C++98) war historisch die Regel: wer einen Destruktor schreibt, schreibe auch Copy-Ctor und Copy-Assignment. Sonst: Compiler-generierter Copy-Ctor + selbst geschriebener Destruktor → Doppel-Free.
  • Rule of 5 (C++11) ergänzt um Move-Ctor und Move-Assignment, sonst schaltet die Klasse Move-Optimierungen aus.
  • Beispiel: class Sensor { std::string name_; std::vector<double> values_; };, kein einziger Spezialmember nötig. Compiler macht alles richtig (Rule of 0).
  • Anti-Beispiel: class Buffer { char* data_; ... };, du brauchst alle 5. Aber genau diese Klasse solltest du nicht selber schreiben: nimm std::vector<char>.
  • Faustregel-Statement wiederholen: nur Klassen, die eine konkrete Ressource direkt halten (selten in modernem Code).

Von manueller Speicherverwaltung zu Smart Pointern

Rohe Pointer zeigen auf Speicher, aber sie sagen nicht, wem das Objekt gehört.

  • T* beschreibt Zugriff, aber keine Ownership.
  • Unklare Ownership → Leaks, Double-Free, Use-after-free, fehlendes Exception-Cleanup.
  • Smart Pointer machen Ownership zum Teil des Typs:
    • std::unique_ptr<T>: exklusiver Besitzer
    • std::shared_ptr<T>: geteiltes Ownership
    • std::weak_ptr<T>: beobachtet ohne Besitz
  • Cleanup passiert automatisch im Destruktor des Smart Pointers → RAII in Aktion.
  • Kernregel modernen C++: new/delete im Anwendungs-Code möglichst vermeiden.

→ Nächster Abschnitt: unique_ptr, shared_ptr, weak_ptr, wann welcher?

  • Brücken-Folie zum nächsten Abschnitt: Rückgriff auf die 5 Fallen („Ownership ist der Kern“).
  • T* beschreibt Zugriff, aber keine Ownership: Schlüsselsatz. Man kann auf etwas zugreifen, ohne es zu besitzen.
  • Drei Smart-Pointer-Rollen vorstellen, ohne tiefer einzusteigen, kommen alle in Teil VI ausführlich.
  • unique_ptr = „ein Owner“. Default-Wahl.
  • shared_ptr = „geteiltes Ownership“. Nur wenn nötig: atomare Refcount-Updates kosten was.
  • weak_ptr = „beobachten ohne Besitz“. Gegenstück zu shared_ptr: bricht Zyklen, beobachtet Caches.
  • Cleanup automatisch im Destruktor: RAII direkt in Aktion. Pendant zu try-with-resources.
  • Kernregel: im Anwendungscode niemals mehr new/delete. Bibliotheks-Code (Smart Pointer-Implementierung selbst) darf, der Anwender nicht.

Teil VI: Smart Pointer

std::unique_ptr: exklusives Ownership

Ein klarer Owner, automatische Freigabe, keine Kopien, nur Move.

auto p = std::make_unique<Sensor>("temp-1", 80.0);

if (p->triggers(85.0)) { /* Sensor hat ausgelöst */ }    // wie normaler Pointer

// nicht kopierbar, aber movebar
auto q = std::move(p);                   // Ownership wandert von p nach q;
                                         // p ist danach leer (== nullptr)
// auto r = q;                           // Compile-Fehler: Kopieren verboten

std::vector<std::unique_ptr<Sensor>> sensors;
sensors.push_back(std::move(q));         // Ownership wandert in den vector
  • Automatische Freigabe beim Zerstören (RAII) · kein Ownership-Overhead gegenüber Raw-Pointer
  • Statt new/delete von Hand: immer std::make_unique<T>(args…)
  • unique_ptr = Default-Wahl: wann immer du dynamische Objekte mit klarem Owner brauchst.
  • make_unique statt new: ist exception-safe, einfacher zu lesen, kein doppeltes Schreiben des Typs.
  • Wie ein Raw-Pointer benutzbar: p->method(), *p, if (p), alles gleich. Der Smart Pointer ist transparent.
  • Move-Semantik: auto q = std::move(p) überträgt Ownership. p ist danach nullptr. Kein Klonen, der Heap-Block hat einen neuen Besitzer.
  • Compile-Fehler bei Copy (auto r = q;) ist ein Feature, kein Bug: verhindert Double-Free strukturell.
  • In Container packen: vector<unique_ptr<T>>, typisches Pattern für polymorphe Hierarchien (siehe Teil IV).
  • Performance: unique_ptr<T> ist binär identisch zu T*, kein Overhead in Code oder Speicher (mit Default-Deleter).
  • Demo-Idee: zeigen, was passiert, wenn man versucht zu kopieren, der Compiler-Fehler ist sehr explizit (MSVC: C2280 „attempting to reference a deleted function“). Projekt 07_smart_pointer.

std::shared_ptr: geteiltes Ownership

Mehrere Besitzer, automatische Freigabe beim letzten. Lebensdauer wird über einen Referenzzähler verwaltet.

#include <memory>

auto s1 = std::make_shared<Config>();

auto s2 = s1;                  // beide besitzen dasselbe Objekt
                               //   s1 ─┐
{                              //   s2 ─┼──> Config
    auto s3 = s1;              //   s3 ─┘
}                              // s3 weg, Objekt bleibt erhalten

// Objekt wird erst gelöscht, wenn der letzte shared_ptr zerstört wurde

auto s2 = s1; ist keine Kopie des Objekts, es wird nur ein weiterer Besitzer erzeugt.

  • Refcount-Overhead: Kopieren/Zerstören kostet atomare Operationen
  • Unklare Besitzverhältnisse: wer ist der „echte“ Owner?
  • Zyklen: zwei shared_ptr können sich gegenseitig am Leben halten → Leak
  • Refcount erklären: intern speichert shared_ptr einen Counter. Bei Copy: ++count. Bei Destruktion: --count. Bei count == 0: Objekt freigeben.
  • Diagramm im Code: drei shared_ptrs zeigen alle auf dasselbe Config-Objekt. Eine Allokation, drei Besitzer.
  • Wichtig zu betonen: auto s2 = s1; ist keine Objekt-Kopie, nur ein zusätzlicher Besitzer. Das Config-Objekt existiert nur einmal.
  • Refcount-Overhead ist nicht null: atomare Increment/Decrement mit Memory-Barrier. In Hot-Loops messbar.
  • Unklare Besitzverhältnisse: wenn jeder shared_ptr haben kann, weiß keiner mehr, wer „verantwortlich“ ist. Schlechtes Design.
  • make_shared vorziehen: allokiert Refcount-Block + Objekt zusammen in einem Aufruf, eine Allokation statt zwei.
  • Pendant in anderen Sprachen: Pythons Refcount, Objective-C ARC. Java/C# haben Tracing-GC, das ist anders.
  • Wann shared_ptr berechtigt: Cache mit mehreren Lookern, Observer-Pattern wo Listener mehrfach in Listen, Resource-Pool. Nicht als „Universal-Pointer“.
  • VS-Tipp: im Debugger zeigt das Überwachungsfenster bei einem shared_ptr direkt [Uses]/[Weaks], Refcount live mitverfolgen.

Zyklische Referenzen und weak_ptr als Lösung

Zwei shared_ptrs, die sich gegenseitig halten, kommen nie auf Refcount 0 → Speicherleck.

struct A { std::shared_ptr<B> b; };
struct B { std::shared_ptr<A> a; };          // ⚠ Zyklus: A ↔ B halten sich gegenseitig
struct A { std::shared_ptr<B> b; };
struct B { std::weak_ptr<A>   a; };          // ✓ B beobachtet A, besitzt es nicht

Faustregel: in einer Hierarchie hält der Parent den Child per shared_ptr, der Child verweist auf den Parent per weak_ptr.

Verwende std::shared_ptr nur, wenn mehrere Stellen wirklich gemeinsam Ownership haben. Sonst ist std::unique_ptr die bessere Default-Wahl.

  • Zyklus-Problem: Refcount kommt nie auf 0, weil A B besitzt und B A. Refcount bleibt 1 ↔︎ 1, also ein Leak.
  • Demo-Idee: Code mit zwei shared_ptrs schreiben, mit Destruktor-printout. Zeigen, dass Destruktoren am Programm-Ende nicht laufen → Leak. (Genau das ist Aufgabe 4 in 07b_smart_pointer_uebung.)
  • Lösung: EINEN der beiden Pointer auf weak_ptr umstellen. Der weak_ptr erhöht den Refcount nicht.
  • Faustregel „Parent shared, Child weak“: typische Hierarchie: Eltern besitzt Kinder; Kinder verweisen rückwärts ohne Besitz.
  • Auch in anderen Mustern: Observer-Pattern (Subject hält Observer per shared, Observer kennt Subject per weak), Caches.
  • Schluss-Statement noch mal: shared_ptr nur wenn nötig, Default ist unique_ptr.

std::weak_ptr: beobachten ohne Ownership

Nicht-besitzender Beobachter für Objekte, die von shared_ptr verwaltet werden. Verlängert die Lebensdauer nicht.

#include <memory>

std::shared_ptr<Node> parent = /* ... */;

std::weak_ptr<Node> observer = parent;     // besitzt nicht, kein Refcount++
if (auto p = observer.lock()) {            // versucht shared_ptr zu erlangen
    p->do_something();                     // Objekt existiert noch
} else {
    // Objekt wurde bereits gelöscht
}
Einsatz Warum weak_ptr?
Parent-Child-Beziehungen Rückverweis soll das Parent-Objekt nicht künstlich am Leben halten
Caches Objekt darf verschwinden, wenn es sonst niemand mehr braucht
Observer-Pattern Beobachter besitzt das beobachtete Objekt nicht

Merksatz: shared_ptr besitzt · weak_ptr beobachtet · lock() macht daraus kurzzeitig wieder einen sicheren shared_ptr.

  • weak_ptr ist nicht direkt benutzbar: kein * und kein ->, du musst erst lock() aufrufen.
  • lock() ist atomar: entweder gelingt es (du kriegst einen gültigen shared_ptr zurück, Refcount erhöht) oder das Objekt ist schon weg (lock() gibt leeren shared_ptr zurück).
  • Typische Verwendung: if (auto p = w.lock()) { p->...; }, wenn das Objekt noch lebt, benutze es; sonst überspringen.
  • Drei klassische Einsätze durchgehen:
    • Parent-Child: Child weiß, wer Parent ist, hält ihn aber nicht am Leben
    • Cache: weak_ptr-Map als Cache; sobald sonst niemand das Objekt hält, kann der Cache es gehen lassen
    • Observer-Pattern: Listener registriert sich als weak_ptr; Subject nutzt lock() beim Notify, fragt automatisch ab, ob Listener noch existiert
  • Merksatz auf der Folie ist die kompakteste Zusammenfassung: „shared_ptr besitzt, weak_ptr beobachtet, lock macht daraus shared“.

Situation Verwende
Einzelner Owner, dyn. Objekt std::unique_ptr<T>
Mehrere Owner, unklarer Lifetime std::shared_ptr<T>

Faustregel: make_unique / make_shared, nie new direkt.

  • Zusammenfassungs-Folie: als Cheatsheet/Daumenregel für die Praxis.
  • Default ist immer unique_ptr: kostet nichts, drückt klare Ownership aus.
  • shared_ptr nur wenn die Lebenszeit wirklich von mehreren Stellen abhängt, und keine davon dominiert.
  • weak_ptr für Rückverweise / Observer / Caches.
  • Reine Beobachter brauchen keinen Smart Pointer: T* (bei optional) oder const T& (bei pflicht) reicht. Smart Pointer sind für Ownership, nicht für Beobachtung.
  • Arrays: std::vector<T> ist fast immer besser als unique_ptr<T[]>, Wachstum, bessere API, gleiche Effizienz.
  • make_unique/make_shared statt new: exception-safe (bei f(make_x(), make_y()) kann zwischen den Konstruktionen kein Leak entstehen) und kürzer.

Teil VII: Generische Programmierung

Function Templates

template <typename T>
T max_of(const T& a, const T& b) {                    // ← Rückgabetyp T:
    return (a < b) ? b : a;                           //   beide Argumente
}                                                     //   müssen denselben Typ haben

max_of(3, 7);                                  // erzeugt max_of<int>
max_of(2.5, 1.8);                              // erzeugt max_of<double>
max_of(std::string{"a"}, std::string{"b"});    // erzeugt max_of<std::string>

// max_of(3, 2.5);                             // ⚠ Compile-Fehler, T mehrdeutig:
                                               //   int oder double?

Function Template = Funktions-Schablone. Der Compiler leitet T aus den Argumenten ab und erzeugt bei Bedarf eine konkrete Funktion daraus (max_of<int>, max_of<double>, …). Das Template selbst ist noch kein Code: Code entsteht erst durch die Instanziierung.

  • Eindeutigkeit: beide Parameter müssen den gleichen abgeleiteten Typ ergeben, sonst Compile-Fehler.
  • Workaround für gemischte Typen: zwei Template-Parameter (<typename T, typename U>) oder explizite Angabe max_of<double>(3, 2.5).
  • Wichtigster Punkt zuerst: ein Template ist noch kein Code. Es ist eine Schablone, aus der der Compiler bei Bedarf Code erzeugt.
  • Instanziierung: der Begriff steht für „Compiler erzeugt aus dem Template eine konkrete Funktion für den abgeleiteten Typ“.
  • Template-Parameter T ist nur ein Platzhalter: Konvention Großbuchstabe, könnte auch Foo heißen.
  • Drei Aufrufe demonstrieren Type-Deduktion: int, double, std::string. Jedes Mal entsteht eine eigene Funktion.
  • max_of(3, 2.5) als Compile-Fehler zeigen: T müsste gleichzeitig int und double sein. Das geht nicht.
  • Workarounds: Entweder zwei Template-Parameter (<T, U>) oder explizit max_of<double>(3, 2.5) (dann wird 3 zu double konvertiert).
  • Code-Bloat-Warnung (nicht auf Folie, aber erwähnen): pro Typ entsteht eine eigene Funktion im Binary. Bei vielen Typen kann das die Executable-Größe treiben.
  • Java/C#-Pendant: Generics, aber dort findet die „Instanziierung“ zur Laufzeit / Type-Erasure statt. C++ macht alles zur Compile-Zeit.

Class Templates

template <typename T, std::size_t N>            // T = Typ-Parameter
class RingBuffer {                              // N = Nicht-Typ-Parameter
public:                                         //     (Compile-Time-Wert)
    void push(const T& v) {
        data_[head_] = v;
        head_ = (head_ + 1) % N;
        if (size_ < N) ++size_;
    }
private:
    std::array<T, N> data_{};
    std::size_t head_ = 0;
    std::size_t size_ = 0;
};

RingBuffer<double, 16>     recent_temps;        // T=double,   N=16
RingBuffer<LogEntry, 1000> log;                 // T=LogEntry, N=1000

Class Template = Klassen-Schablone. T bestimmt den Elementtyp, N eine feste Größe zur Compile-Zeit. Der Compiler erzeugt aus jedem <T, N>-Paar eine eigene konkrete Klasse.

  • Zwei Arten von Template-Parametern:
    • Typ-Parameter (typename T oder class T): typischer Fall
    • Nicht-Typ-Parameter (std::size_t N): ein Compile-Time-Wert (Zahl, Pointer, Bool)
  • std::array<T, N> ist das beste Beispiel für Nicht-Typ-Parameter: Größe ist Teil des Typs, nicht der Daten.
  • RingBuffer<double, 16> und RingBuffer<double, 17> sind verschiedene Klassen: Compiler generiert beide separat, mit jeweils 16 bzw. 17 Slots.
  • STL-Beispiele: std::vector<T>, std::map<K, V>, std::pair<T, U>, std::optional<T>, std::array<T, N>.
  • Performance: weil die Größe N Compile-Zeit-Konstante ist, kann der Compiler aggressiv optimieren, Schleifen ausrollen, Indizes inlinen.
  • Demo-Idee: ein std::array<int, 5> mit static_assert(sizeof == 20) zeigen, die Größe ist statisch bekannt.

Concepts (C++20): Typsichere Templates

Concepts beschränken Templates auf Typen, die bestimmte Eigenschaften erfüllen. Pendant zu Rust-Traits oder Java-Interfaces, geprüft zur Compile-Zeit, ohne Laufzeit-Overhead.

#include <concepts>

template <std::integral T>             // T muss ganzzahlig sein
T gcd(T a, T b) {
    while (b) { a %= b; std::swap(a, b); }
    return a;
}
gcd(12, 8);                            // ✓ T=int
gcd(2.5, 1.0);                         // ✗ "constraint std::integral<double> not satisfied"

// Eigenes Concept: "T unterstützt a+b, Ergebnis ist wieder T"
template <typename T>
concept Addable = requires(T a, T b) { { a + b } -> std::same_as<T>; };

template <Addable T>  T sum(const std::vector<T>& v);
  • Standard-Concepts in <concepts>: std::integral, std::floating_point, std::copyable, std::same_as, …
  • Concepts sind Constraints: sie schränken ein, welche Typen ein Template akzeptiert.
  • Pendant zu Java/Rust: Java-Generics mit <T extends Number> sagen „T muss von Number erben“. Rust-Traits sagen „T muss Add implementieren“. C++-Concepts machen dasselbe, aber rein zur Compile-Zeit, ohne Laufzeit-Overhead.
  • std::integral T statt typename T ist die Kurzform für eingeschränkte Templates. Lesbar und prägnant.
  • gcd(2.5, 1.0) Compile-Fehler: entscheidender Vorteil gegenüber Templates ohne Concepts: Fehlermeldung sagt direkt „constraint nicht erfüllt“ (MSVC: C2672 „no matching overloaded function found“ + „the associated constraints are not satisfied“), nicht „kein Match für %= mit double“ 200 Zeilen tief.
  • Eigenes Concept mit requires-Expression: liest sich wie ein Pseudo-Code-Test („für T und U muss a + b möglich sein und Typ T zurückgeben“).
  • Pre-C++20 Workaround war SFINAE / enable_if: funktioniert, aber die Fehlermeldungen waren berüchtigt unverständlich.
  • Wann Concepts schreiben: wenn du eine Bibliothek baust, die andere benutzen. Anwendungs-Code nutzt eher fertige Standard-Concepts oder kommt ohne aus.
  • Projekt: 08_templates (Function/Class Template, if constexpr, Concepts).

Teil VIII: Exception Handling

try / catch: Basics

try {
    auto data = load_config("config.json");
    process(data);
} catch (const std::invalid_argument& e) {
    log_error("bad input:", e.what());
} catch (const std::runtime_error& e) {
    log_error("runtime failure:", e.what());
} catch (...) {                      // Catch-all
    log_error("unknown error");
    throw;                           // Weiterwerfen
}
  • Aufbau: try { … } ist der geschützte Block, catch (T) der Handler pro Typ, catch (...) der Fallback.
  • Reihenfolge wichtig: spezifischere zuerst. catch (const std::exception&) würde sonst alles Folgende verschlucken.
  • const T& als Catch-Parameter ist Standard. Vermeidet Slicing (eigener Catch für Derived greift, nicht der für Base).
  • throw; ohne Argument: wirft die aktuelle Exception unverändert weiter. Wichtig: nicht throw e; schreiben, das würde slicen.
  • Keine finally-Klausel: C++ nutzt RAII statt finally. Cleanup passiert in Destruktoren der lokalen Objekte (Stack-Unwinding).
  • VS-Debugger-Tipp: Debuggen → Fenster → Ausnahmeeinstellungen → „C++ Exceptions“ ankreuzen → der Debugger hält beim throw an, nicht erst im catch. Zeigt den Call-Stack im Moment des Wurfs.

Was passiert beim throw? Stack-Unwinding

Wenn eine Exception fliegt, rollt der Stack auf: auf jedem Frame werden lokale Objekte zerstört (Destruktoren laufen), bis ein passender catch gefunden wird.

void inner() {
    std::vector<int> v(1000);             // RAII-Objekt #1
    throw std::runtime_error{"oops"};
}
void middle() {
    std::ifstream f{"data.txt"};          // RAII-Objekt #2
    inner();                              // throw fliegt heraus
}
void outer() {
    try { middle(); }
    catch (const std::exception& e) { /* Handler */ }
}

Reihenfolge beim throw: ~vector(v) → ~ifstream(f) → catch-Handler in outer.

  • Zwischen throw und catch läuft nur Destruktor-Code lokaler Objekte
  • Kein passender Handler: std::terminate → Programm-Abbruch
  • Konsequenz: Cleanup ohne try/finally, funktioniert nur dank RAII
  • Stack-Unwinding ist der Kern-Mechanismus der C++-Exception-Handling. Ohne ihn wäre RAII nutzlos.
  • Pseudo-Animation: Frame für Frame durch den Call-Stack laufen, an jedem Frame Destruktoren auflisten.
  • Demo-Idee: Drei Klassen mit Destruktor-Printout, dazwischen ein throw. Reihenfolge der Destruktor-Aufrufe live zeigen: beweist die Mechanik. Mit Breakpoints in den Destruktoren und dem Fenster „Aufrufliste“ sieht man in VS, dass die Destruktoren aus dem Unwinding heraus aufgerufen werden.
  • Performance: Stack-Unwinding ist teuer, moderne Implementierungen sind aber so optimiert, dass der „Happy Path“ (kein Wurf) null Overhead hat. Nur der Wurf selbst kostet.
  • Vergleich Java/C#: dort gibt es finally als zusätzliches Konstrukt. C++ braucht das nicht, weil Destruktoren die gleiche Aufgabe übernehmen.
  • Wichtige Folge: Destruktoren dürfen nie werfen, wenn beim Unwinding ein Destruktor wirft, gibt es zwei aktive Exceptions → std::terminate.

Eigene Exception-Klassen

class SensorError : public std::runtime_error {
public:
    SensorError(std::string sensor, std::string msg)
        : std::runtime_error{std::move(msg)}, sensor_{std::move(sensor)} {}

    const std::string& sensor() const noexcept { return sensor_; }
private:
    std::string sensor_;
};

throw SensorError{"temp-1", "calibration lost"};
  • Von std::exception / std::runtime_error erben: konsistente Hierarchie
  • what() override für Nachricht
  • Eigene Exceptions sollten von einer Standard-Klasse erben, sonst gibt es keinen gemeinsamen catch (const std::exception&)-Punkt.
  • std::runtime_error vs. std::logic_error als Basis: erstere für Laufzeit-Probleme (Datei nicht da, Netz weg), zweitere für Programmierfehler (falsche Argumente).
  • Zusätzliche Member wie sensor_: typisches Pattern, um Kontext-Informationen mitzugeben.
  • what() override ist optional, wenn man die Basis-Klassen-Implementierung übernimmt, reicht runtime_error{msg} im Konstruktor.
  • Konstruktor noexcept? nein, der Konstruktor selbst darf werfen (z. B. wenn std::string allokiert). Aber what() const noexcept ist im Interface garantiert.
  • Wer wirft, was wirft er? Faustregel: dokumentieren in der Funktions-Doxygen, nicht mit alten throw()-Specs deklarieren (deprecated/entfernt).
  • Projekt: 09_exceptions (SensorError, catch-Reihenfolge, Copy-and-Swap, Destruktor-Regel).

Standard-Hierarchie der Exceptions

std::exception                           ← Basis aller Standard-Exceptions
├── std::logic_error                     ← Programmierfehler
│   ├── std::invalid_argument            ← falsches Argument
│   ├── std::domain_error                ← Wert außerhalb des erlaubten Bereichs
│   ├── std::length_error                ← zu groß / zu klein
│   └── std::out_of_range                ← .at(), Index außerhalb Container
├── std::runtime_error                   ← Laufzeit-Probleme
│   ├── std::range_error                 ← Wertebereich-Überschreitung (Berechnung)
│   ├── std::overflow_error              ← arithmetischer Überlauf
│   └── std::system_error                ← OS-Fehler (errno)
├── std::bad_alloc                       ← new schlägt fehl
├── std::bad_cast                        ← dynamic_cast<T&> schlägt fehl
└── std::bad_optional_access             ← optional::value() leer
  • logic_error = „ich hab Mist gebaut, eigentlich hätte ich’s prüfen müssen“, meist Bug
  • runtime_error = „Welt ist heute schwierig“: Datei weg, Netz weg, Speicher voll
  • Faustregel beim Erben: runtime_error für vorhersehbare Laufzeit-Fehler, logic_error für Bug-Symptome
  • Catch von std::exception fängt alle Standard-Exceptions auf einmal: guter äußerer Sicherheits-Handler
  • Hierarchie auswendig kennen lohnt sich nicht, aber wissen, dass es zwei Hauptzweige gibt (logic_error / runtime_error) und einige spezielle Wurzel-Klassen (bad_alloc, bad_cast).
  • Eigene Exceptions sollten in einen der Zweige eingeordnet werden, nicht direkt von std::exception erben (außer du baust ein eigenes Framework).
  • std::system_error kapselt OS-Fehler mit errno-Code: wichtig für Filesystem/Netzwerk-Code.
  • std::bad_alloc wird von new geworfen, wenn der Heap voll ist. Wird selten gefangen, meist Programm-Ende sinnvoller als Recovery.
  • Pendant zu Java: Exception vs. RuntimeException: Java unterscheidet checked vs. unchecked. C++ kennt diese Unterscheidung nicht (alle Exceptions sind unchecked).
  • Demo-Idee: std::vector::at(99) für std::out_of_range, und sehen, was die Hierarchie hochläuft, wenn man std::exception fängt. (Achtung: v[99] statt v.at(99) wirft nicht, im Debug-Build meldet MSVC stattdessen eine Assertion „vector subscript out of range“.)

Best Practices & Anti-Patterns

✓ Gut ✗ Anti-Pattern
throw MyError{...}; (by value) throw new MyError{...}; (Java-Reflex)
catch (const std::exception& e) (const-ref) catch (std::exception e) (slicing!)
Spezifischere Catches zuerst catch (...) zuerst → andere unerreichbar
Destruktor noexcept (Default) Destruktor wirft → std::terminate
Exception nur für echte Fehler Exception für normalen Kontrollfluss
  • Performance: Happy-Path kostet null, der Wurf ist teuer (~1µs). Daher: Exceptions nur für außergewöhnliche Fälle.
  • Embedded / Game-Engines: dort oft ohne Exceptions kompiliert (-fno-exceptions, MSVC: /EH weglassen). Alternative: Status-Codes, std::expected (siehe nächste Folie).
  • Constructor-Wurf: verhindert ein „halb-konstruiertes“ Objekt. Aufrufer kriegt sauber kein Objekt zurück.
  • Destruktor-Wurf: niemals
  • Das ist die wichtigste Praxis-Folie des Exception-Kapitels. Die Antipatterns sind alle echte Bugs, die in Bestandscode vorkommen.
  • throw new T{}: Java-Reflex. In C++ wirft man by value, der Compiler kümmert sich um Lebenszeit-Verlängerung. new wäre ein Heap-Leak.
  • Slicing beim Catch: catch (std::exception e) kopiert nur den Basis-Anteil. Konkrete Klasse weg, what() zeigt Basis-Text.
  • throw; vs. throw e;: ersteres leitet die ursprüngliche Exception weiter (mit ursprünglichem Stack-Trace), zweiteres macht eine neue Exception aus dem (geslicten) e.
  • Destruktor-Wurf ist die häufigste Ursache für std::terminate in der Praxis. Vor allem in Connection::~Connection() { close(); }, wenn close werfen kann, ist das gefährlich.
  • Exceptions abschalten: gcc/clang -fno-exceptions; MSVC steuert das über /EH, Visual Studio setzt für Konsolenprojekte standardmäßig /EHsc (Standard-C++-Exceptions an, extern "C"-Funktionen werfen nicht). Game-Engines (Unreal hat eine eigene Variante) und Embedded oft ohne. Standard-Library funktioniert dann eingeschränkt.
  • Exception als Kontrollfluss (z. B. „End of File“-Exception) ist langsam und unidiomatisch, std::optional oder ein Status-Code sind besser.

std::expected<T, E>: die moderne Alternative (C++23)

Erfolgswert oder Fehler: eines von beiden, typsicher in einem Container. Pendant zu Rusts Result<T, E> und Haskells Either. Ideal wenn Fehler erwartbar sind und nicht außergewöhnlich.

#include <expected>

enum class ParseError { EmptyInput, InvalidChar, OutOfRange };

std::expected<int, ParseError> parse_int(std::string_view s) {
    if (s.empty()) return std::unexpected{ParseError::EmptyInput};
    int v{};
    auto [_, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{}) return std::unexpected{ParseError::InvalidChar};
    return v;
}

if (auto r = parse_int("42"); r) std::cout << *r;          // ✓ Erfolg
else                              std::cout << static_cast<int>(r.error());
  • Kein Throw / Unwinding → schnell wie Status-Code, typsicher wie Exception
  • Wann was: Exceptions für außergewöhnliche Fehler · expected für erwartbare · optional wenn nur „ja/nein“
  • std::expected ist C++23, also in vielen Codebases noch nicht verfügbar. MSVC hat es seit VS 2022 17.3 mit /std:c++latest (Projekt → C/C++ → Sprache → C++-Sprachstandard „Vorschau“), die Schulungsprojekte stehen bereits darauf, die Demo läuft in 10_modern_cpp (Abschnitt C++23, parse_port). Boost hat es seit Jahren, und tl::expected ist eine Header-Only-Backport-Bibliothek.
  • Konzept verstehen ist wichtiger als die genaue API: Rust/Haskell/Scala-Entwickler kennen das Pattern als Result<T, E> / Either E A / Try[T].
  • Vergleich zu Exceptions:
    • Exception = „Außergewöhnlich, sollte nicht passieren, Stack-Unwinding teuer“
    • expected = „Erwartbar, kommt häufig vor, expliziter Kontrollfluss“

  • Klassisches Beispiel-Projekt: Parser, Konfig-Reader, HTTP-Client, alles, wo Fehler Routine sind und aussagekräftige Diagnostik wichtig ist.
  • In der Praxis: Boost.Outcome und tl::expected sind die typischen Backports für Codebases auf C++17/20.

Exception-Safety: Garantien

Level Kurz gesagt
No-throw Kann nicht fehlschlagen (noexcept)
Strong Fehler? Alles bleibt wie vorher (Commit-or-Rollback)
Basic Fehler? Objekt bleibt benutzbar, keine Leaks
No guarantee Fehler? Zustand nach Exception nicht garantiert, vermeiden

Exception-Safety beschreibt, was nach einem Fehler garantiert noch stimmt. RAII sorgt dafür, dass Ressourcen auch bei Exceptions sauber freigegeben werden.

  • RAII ist das Werkzeug: automatisches Cleanup bei Stack-Unwinding
  • noexcept auf Move-Operationen hilft STL-Containern, Move statt Copy zu nutzen
  • Keine Exceptions aus Destruktoren! → sonst std::terminate
  • Vier Garantie-Stufen als formale Hierarchie. Schwächste oben, stärkste unten, auch andersrum lesbar.
  • No-throw / nothrow: noexcept-Methoden. Kann der Compiler/STL für Optimierungen nutzen (z. B. vector reserviert anders bei noexcept-Move).
  • Strong = „transactional“ = „commit or rollback“. Beispiel: std::vector::push_back, wenn der Move/Copy ins neue Buffer wirft, wird der alte Vector nicht angetastet.
  • Basic = „kein Leak, Invarianten halten“. Aber Zustand kann sich geändert haben. Default für die meisten Operationen.
  • No guarantee ist ein Bug und sollte in produktivem Code nicht vorkommen.
  • noexcept auf Moves ist die wichtigste praktische Anwendung: ohne noexcept-Move kopiert std::vector bei Realloc statt zu moven (Strong-Garantie zu erhalten).
  • „Keine Exceptions aus Destruktoren“ noch mal hervorheben, das ist die Falle Nr. 1 in der Praxis.
  • Kontrast Java/C#: dort gibt es die formale Stufung nicht, try-with-resources/using macht’s leichter, aber weniger granular.

Teil X: Coroutines & std::generator

Lazy Sequenzen: Werte erst dann berechnen, wenn sie gebraucht werden.

Lazy Sequenzen: das Problem

Eager: alles vorab berechnen

std::vector<int> fib_first(int n) {
    std::vector<int> out;
    int a = 0, b = 1;
    for (int i = 0; i < n; ++i) {
        out.push_back(a);
        int t = a + b; a = b; b = t;
    }
    return out;             // n muss vorher bekannt sein
}

Speicher für alle Werte, Abbruchkriterium im Erzeuger, keine unendlichen Folgen.

Lazy: Werte auf Abruf

std::generator<int> fibonacci() {
    int a = 0, b = 1;
    while (true) {          // unendlich, kein Problem
        co_yield a;         // Wert liefern, hier pausieren
        int t = a + b; a = b; b = t;
    }
}

for (int x : fibonacci() | std::views::take(10))
    std::cout << x << ' ';

Der Verbraucher entscheidet, wie viel gerechnet wird.

  • Umsteiger kennen das: C# IEnumerable<T> + yield return, Python yield, JavaScript function*
  • In C++ seit C++20 als Coroutine (co_yield), seit C++23 fertig verpackt als std::generator<T>
  • Einstieg über das Bekannte: fast jeder im Raum hat yield return (C#) oder Python-Generatoren benutzt. C++ hat jetzt dasselbe Konzept, nur später bekommen.
  • Eager-Variante ist der Normalfall in altem C++-Code: Container füllen, zurückgeben. Nachteile: Speicher für alles, Erzeuger muss wissen, wann Schluss ist.
  • Lazy-Variante: while (true) ist kein Bug, die Coroutine läuft nur so weit, wie take(10) Werte abholt.
  • Demo: Projekt 10b_generator, demo_basics(), bei count_to(3) sieht man am Ausgabe-Interleaving, dass Erzeuger und Verbraucher sich abwechseln.
  • Voraussetzung nennen: VS 2022 ab 17.13, /std:c++latest (im Projekt gesetzt). Ältere VS-Version → #error mit Klartext.

std::generator: Beispiel

#include <generator>                                     // C++23

std::generator<int> count_to(int n) {
    for (int i = 1; i <= n; ++i) {
        co_yield i;                                      // Wert nach außen, Funktion pausiert
    }
}                                                        // Ende → Sequenz zu Ende

std::generator<const std::string&> read_lines(std::string text) {   // Referenz: keine Kopie pro Zeile
    std::istringstream in{std::move(text)};
    for (std::string line; std::getline(in, line); )
        co_yield line;
}

for (int x : count_to(3))            std::cout << x;     // 1 2 3
for (const auto& l : read_lines(s))  std::cout << l;     // zeilenweise, lazy
  • co_yield macht die Funktion zur Coroutine, der Rückgabetyp std::generator<T> sagt dem Compiler, wie
  • Lazy: die Funktion läuft erst beim ersten Element los und pausiert nach jedem co_yield
  • std::generator<T> liefert T (kopiert), std::generator<const T&> liefert Referenzen auf den Wert im Frame
  • co_yield i: Wert wird „nach außen gereicht“, der Zustand (i, n, Position) bleibt erhalten. Beim nächsten ++it des Verbrauchers geht es hinter dem co_yield weiter.
  • Rückgabetyp entscheidet: ohne std::generator als Rückgabetyp wäre co_yield ein Compile-Fehler, der Typ bringt den promise_type mit (nächste Folie).
  • Referenz-Variante: std::generator<std::string> würde jede Zeile beim co_yield line kopieren (lvalue → Kopie). std::generator<const std::string&> reicht nur eine Referenz auf line im Coroutine-Frame heraus, die lebt, solange die Coroutine pausiert.
  • Parameter by value (std::string text): Absicht, kommt bei den Fallstricken.
  • Debugger-Demo in VS: Breakpoint auf co_yield, F10 → man landet im Verbraucher; nächstes ++it → wieder hinter dem co_yield. Aufrufliste zeigt resume aus dem Iterator.

Was passiert bei co_yield? Die Mechanik

Die Kontrolle pendelt bei jedem co_yield und jedem ++it zwischen Verbraucher und Coroutine, auf einem Thread. Der Coroutine-Frame hält i, n und die Wiedereinstiegsstelle über jede Pause hinweg.

  • Das Diagramm ist der Kern: Zeit läuft nach unten. Graue Pfeile sind Kontrollübergaben vom Verbraucher (begin(), ++it, jeweils ein resume()), blaue gestrichelte Pfeile sind die co_yield-Rückgaben. Die Balken zeigen, wer gerade rechnet: nie beide gleichzeitig. Coroutine ≠ Thread, das ist der häufigste Denkfehler.
  • Erste Zeile: count_to(3) legt nur den Frame an, der Body läuft noch nicht (lazy, initial_suspend liefert suspend_always). Erst begin() startet ihn.
  • Letzte Zeilen: nach co_yield 3 läuft das ++it die Funktion bis zum Ende, done() wird true, der Iterator ist end(). Den Frame räumt der Destruktor des std::generator-Objekts weg (destroy()), nicht das Funktionsende.
  • Frame auf dem Heap: deshalb überlebt der Zustand die Pause. Eine Allokation pro Generator-Objekt, der Compiler darf sie wegoptimieren (HALO), MSVC tut das selten. Für Datenverarbeitung egal.
  • Debugger-Demo (VS): Breakpoint auf co_yield, F10, man landet im Verbraucher; nächstes ++it, wieder hinter dem co_yield. Aufrufliste zeigt resume aus dem Iterator.

Coroutine: die Bausteine im Überblick

Sobald der Compiler co_yield im Funktionskörper sieht, baut er die Funktion zu einer State-Machine um. Was er dafür anlegt:

  1. Coroutine-Frame: Objekt (typisch auf dem Heap) mit Parametern, lokalen Variablen und Wiedereinstiegspunkt
  2. promise_type: Protokoll zwischen Compiler und Rückgabetyp: initial_suspend, yield_value, final_suspend, unhandled_exception
  3. Suspend-Points: jedes co_yield wird zur Pause-Stelle, die Kontrolle geht an den Verbraucher zurück
  4. std::coroutine_handle: „Zeiger“ auf den Frame mit resume(), done(), destroy()
  5. Rückgabeobjekt: das std::generator<T>, das der Aufrufer bekommt, es besitzt den Handle und zerstört den Frame im Destruktor

std::generator implementiert promise_type + Iterator für uns. Vor C++23 hat das jede Codebasis selbst geschrieben (cppcoro, eigene Generator<T>). Im Quellcode sehen wir von alldem nur co_yield.

  • promise_type nur benennen, nicht durchdeklinieren: der Compiler ruft beim Start initial_suspend() (Generator: suspend_always → lazy), bei co_yield yield_value(v), am Ende final_suspend(), bei Exception unhandled_exception().
  • std::coroutine_handle ist nicht-besitzend: wer ihn hält, muss destroy() selbst aufrufen. Deshalb steckt er immer in einem Wrapper (std::generator, eigenes Task<T>), der das im Destruktor erledigt. RAII wie überall.
  • Rückgabetyp entscheidet: ohne std::generator (oder einen anderen Typ mit promise_type) ist co_yield ein Compile-Fehler. Der Typ bringt das Protokoll mit.
  • Historie: C++20 brachte nur die Sprachmittel (co_yield, <coroutine>), aber keinen fertigen Generator, deshalb überall cppcoro::generator, Generator<T>-Boilerplate. C++23 liefert ihn nach.
  • Vergleich: Python yield, C# yield return, JavaScript function*: gleiche Idee, dort aber als fertige Bibliothek. C++ ist mächtiger und anstrengender: Sprach-Feature ohne fertigen Wrapper (bis C++23).

std::generator ist eine View (Input-Range), alle Range-Adapter funktionieren:

for (int x : fibonacci() | std::views::filter([](int v) { return v % 2 == 0; })
                         | std::views::take(5))            // 0 2 8 34 144
    std::cout << x << ' ';

Rekursion mit std::ranges::elements_of, die Werte des inneren Generators werden 1:1 durchgereicht:

struct Node { int value; std::vector<Node> children; };

std::generator<int> walk(const Node& n) {
    co_yield n.value;                                      // erst der Knoten ...
    for (const Node& c : n.children)
        co_yield std::ranges::elements_of(walk(c));        // ... dann alle Kinder rekursiv
}
for (int v : walk(tree)) std::cout << v << ' ';            // 1 2 4 5 3  (Tiefensuche)
  • View-Eigenschaft ist der große Gewinn gegenüber selbstgebauten Generatoren: take, filter, transform, ranges::to, alles ohne Extra-Code.
  • take(5) bricht die unendliche Folge ab: die Coroutine wird danach zerstört (Frame weg), es läuft nichts weiter.
  • elements_of löst das klassische Problem rekursiver Generatoren: ohne es müsste man for (int v : walk(c)) co_yield v; schreiben, funktioniert, ist aber O(Tiefe) pro Element. elements_of hängt den inneren Generator direkt ein (MSVC implementiert das effizient, symmetric transfer).
  • Demo: 10b_generator, demo_recursive(), Baum 1-(2-(4,5)),3 → Ausgabe 1 2 4 5 3.
  • Praxisfälle nennen: Verzeichnisbaum, JSON/AST traversieren, Paginierung einer API, zeilenweises Parsen großer Dateien.

Fallstricke & Regeln

std::generator<int> evens(const std::vector<int>& v) {      // ⚠ Referenz-Parameter
    for (int x : v) if (x % 2 == 0) co_yield x;
}
for (int x : evens({1, 2, 3, 4})) …    // ✗ Temporär stirbt am Zeilenende, Coroutine liest später → UB
Regel Warum
Parameter, die nach einer Pause noch gebraucht werden, by value wandern in den Frame; Referenzen auf Temporäre hängen
Genau ein Durchlauf (Input-Range) zweiter Durchlauf → Generator neu erzeugen
Move-only, wie unique_ptr ein Frame, ein Besitzer
Exceptions fliegen beim Weiterlaufen (begin(), ++it) nicht beim Erzeugen des Generator-Objekts
Coroutine ≠ Thread alles auf einem Thread; für Parallelität weiter std::thread/async

  • Dangling-Beispiel ist der Klassiker und derselbe Fehler wie bei Lambdas mit [&]-Capture, die den Scope überleben. walk(const Node&) auf der Vorfolie ist ok, weil der Baum die Iteration garantiert überlebt, den Unterschied explizit machen.
  • Ein Durchlauf: auto g = count_to(3); for (…: g) …; for (…: g) …;, zweite Schleife liefert nichts. Bei Bedarf Funktion nochmal aufrufen.
  • Move-only: auto g2 = g; ist Compile-Fehler (C2280). Zurückgeben aus Funktionen geht (Move/NRVO).
  • Exceptions: wer try um den Aufruf count_to(3) legt, fängt nichts, der Wurf passiert erst in begin()/++it. try gehört um die Schleife.
  • Coroutine ≠ Thread noch einmal deutlich sagen: Umsteiger aus C# verwechseln yield gern mit async/Task.

std::move: Cast zu rvalue

std::vector<int> a{1, 2, 3, 4, 5};

std::vector<int> b = std::move(a);     // b übernimmt typischerweise den Speicher
                                       // a bleibt gültig, Zustand unspezifiziert, nicht verlässlich

std::string s1 = "hello";
std::string s2 = s1;                   // Copy
std::string s3 = std::move(s1);        // Move

Merke: std::move bewegt selbst nichts. Es markiert ein Objekt nur als „darf bewegt werden“ (Cast zu rvalue). Der eigentliche Move passiert im Move-Konstruktor oder Move-Assignment des Typs.

Rule of Five

class Buffer {
public:
    explicit Buffer(std::size_t n) : data_{new char[n]}, size_{n} {}
    ~Buffer()                      { delete[] data_; }

    Buffer(const Buffer& other);             // Copy-Ctor
    Buffer& operator=(const Buffer& other);  // Copy-Assign

    Buffer(Buffer&& other) noexcept          // Move-Ctor
        : data_{other.data_}, size_{other.size_}
    {
        other.data_ = nullptr;
        other.size_ = 0;
    }
    Buffer& operator=(Buffer&& other) noexcept;   // Move-Assign

private:
    char*       data_{nullptr};
    std::size_t size_{0};
};

Wer eine Ressource direkt besitzt, muss Copy/Move/Destruktor bewusst regeln. Sonst: Rule of 0 bevorzugen, std::vector, std::string, std::unique_ptr erledigen das automatisch.

Perfect Forwarding

template <typename T, typename... Args>
std::unique_ptr<T> make_mine(Args&&... args) {
    return std::make_unique<T>(std::forward<Args>(args)...);
}

auto s = make_mine<Sensor>("temp-1", 80.0);

Idee: Argumente werden an den Konstruktor von T weitergereicht, ohne ihre lvalue/rvalue-Eigenschaft zu verlieren. Kommt außen ein rvalue rein, soll innen auch ein rvalue ankommen.

  • Args...: beliebig viele Argument-Typen (Variadic Template)
  • Args&&... args: Forwarding-References (keine rvalue-Refs, sie entstehen erst durch Template-Deduktion)
  • std::forward<Args>(args)...: leitet jedes Argument genau so weiter, wie es angekommen ist
  • Typischer Einsatz: Factory-Funktionen, Container-emplace, generische Wrapper

std::move vs. std::forward: Merksatz

std::move sagt: „Dieses Objekt darf bewegt werden.“ std::forward sagt: „Gib das Argument genau so weiter, wie es angekommen ist.“

Warum nicht einfach args... statt std::forward<Args>(args)...?

return std::make_unique<T>(args...);     // ⚠ verliert Move-Information

Innerhalb der Funktion haben args Namen, und alles mit Namen ist ein lvalue. Auch wenn außen ein rvalue reinkam, wäre args innen plötzlich ein lvalue → Move-Semantik geht verloren.

Note

Perfect Forwarding braucht man vor allem beim Schreiben generischer Bibliotheksfunktionen. Im normalen Anwendungscode kommt man oft lange ohne aus.

Move-Semantik: Richtlinien

  • Rule of 0 zuerst: STL-Member erledigen Moves meist automatisch
  • Move-Operationen noexcept, wenn sie wirklich nicht werfen können, sonst nutzen STL-Container Copy statt Move (Exception-Safety)
  • Nach std::move(x): x bleibt gültig, aber sein Wert ist nicht mehr verlässlich. Erlaubt: Zuweisung, Destruktion, andere spezifizierte Operationen
  • Für Sink-Parameter oft idiomatisch: Parameter by value, dann std::move in den Member
  • return x; statt return std::move(x);: NRVO und impliziter Move wirken automatisch; explizites std::move blockiert NRVO
